Two knobs decide what a vector query costs: how many vectors you search, and how wide each one is. I wanted the actual shape of both curves on real hardware, and I wanted to know how far napkin math gets you before it stops matching.

So, four sweeps. Brute-force scan and HNSW, each swept over dataset size (100k to 10M at 256-dim) and over embedding dimension (128 to 1536 at 1M vectors), and each run twice: once at fp32, once under binary quantization.

Everything here is latency and build time. I haven't measured recall yet, so read every binary-quant number as the speed half of a tradeoff whose cost half is still open.

**What this ran on.** All numbers are measured with [`bfb`](https://github.com/qdrant/bfb) against a single-node **Qdrant Cloud cluster — 2 vCPU, 8 GiB RAM, ARM (Graviton), Qdrant 1.18.2** — driven from a separate 2-vCPU EC2 box in the same region. Latency is **server-side p50 at 8 concurrent queries** (`-p 8`) on random vectors unless stated otherwise. Single run — treat as preliminary. (One gotcha: the node's telemetry reports the _16-core / 64 GB host_ it's packed onto, not the 2 vCPU / 8 GiB quota that actually bounds it — every number here reflects the quota.)

## Results: brute-force scaling

First, dataset-size scaling with HNSW disabled (`indexing_threshold = 0`) so every query is a full scan. Random 256-dim vectors, 2000 queries per point (500 for the ≥5M cells).

**Rule of thumb.** A brute-force query reads the entire dataset once, so its latency is just how long that read takes: **fp32 ≈ dataset-GB / 30 seconds** (this node scans ~30 GB of vectors a second). Binary quant is 32× smaller and ~13× faster. Both effects fold into one product of dataset size $N$ and dimension $d$:

$$
t \approx \frac{N \cdot d}{R}
$$

Fitting single-query latency on this node:

$$
t_{\text{ms}} \approx 1.3\times10^{-7}\,N d \ \text{ (fp32)}, \qquad t_{\text{ms}} \approx 1.0\times10^{-8}\,N d \ \text{ (binary quant)}
$$

Binary quant is ~13×, not the full 32×, because of the rescore: after the 1-bit Hamming scan it re-ranks the top candidates in full precision, and that eats the missing ~2.5×. The rule lands within ~10% across the measured range:

| $N \times d$ | data read (fp32) | fp32: rule → measured | BQ: rule → measured |
| ------------ | ---------------- | --------------------- | ------------------- |
| 100k × 768   | 0.31 GB          | 10.0 → 10.1 ms        | 0.77 → 0.74 ms      |
| 1M × 768     | 3.07 GB          | 100 → 99 ms           | 7.7 → 7.8 ms        |
| 100k × 1536  | 0.61 GB          | 20 → 18 ms            | —                   |
| 1M × 1536    | 6.14 GB          | 200 → 193 ms          | —                   |

That ~30 GB/s isn't a Qdrant number — it's memory bandwidth, and memory bandwidth scales with cores. A full scan is a SIMD sequential read, which [napkin math](https://github.com/sirupsen/napkin-math) pegs at **~20 GiB/s per thread** and **~200 GiB/s fully threaded**: a single core can't keep enough cache-line fetches in flight to saturate the memory channels, so it takes many cores' worth of outstanding requests to get there. Our 2-vCPU slice sits at ~30 GB/s, about two cores' worth of that per-thread rate. So the scan rate isn't a universal constant — it climbs with core count until the channels saturate, which is why our ~30 GB/s is a 2-vCPU figure and a bigger box brute-forces proportionally faster.

But only up to the box's own ceiling: a single socket's aggregate DRAM bandwidth. DDR5 does ~38 GB/s per channel, and a server socket has 8–12 of them, so realized sequential-read bandwidth tops out around **300–500 GB/s per socket** — that's the ~200 GiB/s threaded figure above. Cores stop helping once they issue enough outstanding requests to fill that (by Little's Law, ~27 KB in flight to saturate 300 GB/s at ~90 ns latency, roughly 10–40 cores), and every core past that does nothing for a scan. Concretely: our dbpedia 1M × 1536 fp32 scan runs 193 ms on 2 vCPUs but would take ~20 ms on a full socket at ~300 GB/s — a 10× from cores, then it hits the memory wall and stops. To go faster you change the hardware, not the code: more sockets (with a NUMA tax) or HBM (GPUs at 3–8 TB/s). Binary quant instead shrinks the bytes 32×, which is why it keeps paying off well past the point where more cores don't.

The _same_ product hits a second, harder wall — memory: $N \cdot d \cdot b \le \text{RAM}$ ($b = 4$ bytes fp32, $1/8$ byte BQ). So all of brute force is one number, $N \cdot d$, run against a time wall and a space wall. The two sweeps below slice it one variable at a time (both at 8 concurrent queries, so their absolute latencies run above the single-query rule — read them for the _shape_, linear in $N$ here and in $d$ next).

- The fp32 curve is **not monotonic** — 5M (1849 ms) comes out _slower_ than 10M (1197 ms), and this reproduces across runs even though the node, RAM residency, and segment count (8) are identical. The tails are heavy too (fp32 p99 is 4–5× p50).

## Why the HNSW build costs O(N log N)

Every HNSW insertion is itself a search: to link a new vector you first have to find its neighbours in the graph built so far. Inserting into a graph of $i$ nodes costs $O(\log i)$ to search plus a constant $k$ to write the links, so building the whole graph costs

$$
\sum_{i=1}^{N} \big(O(\log i) + k\big) = \log(1 \cdot 2 \cdot 3 \cdots N) + kN = \log(N!) + kN
$$

Stirling's approximation for large $N$ gives $\log(N!) \approx N \log N - N$, so

$$
\log(N!) + kN \approx N \log N + (k - 1)N
$$

$k$ is constant, which leaves $O(N \log N)$. That's what you trade for the flat search curve, and it's the one cost here you can't engineer away: every vector you add pays $\log N$ just to find out where it belongs.

Both are ~linear in dimension (dashed fits: fp32 `1.39·dim + 495`, R² = 0.96; BQ `0.17·dim + 222`, R² = 0.88) — each of the N log N distance evaluations during construction costs O(dim). fp32's slope is **~8× BQ's** (1.39 vs 0.17 s/dim): the graph is cheap to build under BQ because those distances run on 1-bit-per-dimension codes.

**Rule of thumb.** The one to remember: **a 1M × 768-dim fp32 build is ~30 min on this node; binary quant cuts it ~5×; it grows as `N·log₂N` and linearly in dimension.** When you need a number for a specific dimension, the per-1M-vector cost splits into a fixed part plus a per-dimension part:

- **fp32 ≈ 7 min + (dim / 40) min per 1M vectors**
- **BQ ≈ 4 min + (dim / 340) min per 1M vectors**

| per 1M vectors | fp32    | BQ     |
| -------------- | ------- | ------ |
| 256-dim        | ~13 min | ~4 min |
| 768-dim        | ~30 min | ~6 min |
| 1536-dim       | ~45 min | ~8 min |

These per-1M numbers already bake in the `log₂N` factor at its N=1M value (`log₂(1M) ≈ 20`, frozen into the `7` and the `40`). So for other dataset sizes, multiply by the number of millions of vectors, then nudge up as that log term re-emerges — each doubling of N adds ~5%, so it runs a touch worse than linear. In practice 2M is 2.1× the 1M number (not 2×) and 10M is ~11.7× (not 10×): 10M × 256 fp32 ≈ 13 min × 11.7 ≈ 2.5 h.

Underneath, both sweeps share one structure: the build is `N·log₂(N)` insertions, and each insertion is a distance-guided search whose cost splits into an `O(d)` distance evaluation plus dimension-independent graph bookkeeping (link writes, heap ops). Fold both into one formula in $N$ and $d$:

$$
t_{\text{build}} \approx N \log_2 N \,(\alpha\, d + \beta)
$$

Fitting both sweeps jointly on this node:

$$
\begin{aligned}
\text{fp32:}\quad & \alpha = 7.3\times10^{-8}\,\text{s}, \quad \beta = 2.1\times10^{-5}\,\text{s}\\
\text{BQ:}\quad & \alpha = 8.8\times10^{-9}\,\text{s}, \quad \beta = 1.1\times10^{-5}\,\text{s}
\end{aligned}
$$

$\alpha d$ is the distance evaluation per insertion — fp32 is **8× costlier** than 1-bit codes — and $\beta$ is the bookkeeping, only ~2× between them. At 256-dim this reduces to ≈ $4\times10^{-5}\,N\log_2 N$ s, matching the dataset-size fit above. Because $\alpha d$ and $\beta$ are comparable at 256-dim but $\alpha d$ takes over by 1536, **BQ's build advantage widens with dimension: 2.5× faster at 128-dim, 5.4× at 1536**. The formula holds within ~15% across 100k→10M and 128→1536-dim:

| $N \times d$ | fp32: rule → measured | BQ: rule → measured |
| ------------ | --------------------- | ------------------- |
| 1M × 256     | 787 → 792 s           | 263 → 257 s         |
| 10M × 256    | 9,180 → 9,390 s       | 3,070 → 3,110 s     |
| 1M × 768     | 1,530 → 1,830 s       | 353 → 372 s         |
| 1M × 1536    | 2,650 → 2,510 s       | 489 → 467 s         |

The 1M × 768 row is the worst fit at ~16%, and it sits _above_ the line in both quantizations — one collection that built under extra contention, not a break in the model. Two things to carry away: **doubling the dataset more than doubles the build** (the `log₂N` factor adds ~5% per doubling at this scale, so 1M→2M is 2.1×, not 2×), and **fp32 build cost climbs with dimension while BQ stays near its floor** — which is why quantization is the first lever when your embeddings are wide.

That's the build-time bill. The payoff is on the read side: **search latency stays flat as the dataset grows** — the whole point of HNSW.

Each of the `O(log N)` hops evaluates a handful of distances, and each distance costs `O(dim)` — fp32's per-dim slope is **~5× BQ's** (0.10 vs 0.022 ms/dim), the 1-bit-vs-float distance gap again.

**Rule of thumb.** HNSW search latency doesn't collapse to one law the way the scan and build do — it's a linear-in-dimension term over a fixed floor, with only a weak log-N rise on top. On this node (`-p 8`, index in RAM):

- **fp32 ≈ dim/10 + 8 ms** per query at 1M
- **BQ ≈ dim/45 + 4 ms** per query at 1M
- **N adds a weak log rise:** ~6–7 ms per doubling, so 1M→10M lifts latency ~20 ms, small next to the dimension term. Nearly flat, which is the whole point of the index.
- **Hard limit — RAM:** the vectors must fit, or latency falls off a cliff (10M × 256 fp32 → 51 s). Quantization pushes that wall out 32×, which is why it matters for search and not just storage.

## When to reach for HNSW: the SLA-budget view

HNSW pays off at scale, but it charges for it: an `O(N log N)` build (time + energy), extra RAM for the graph, approximate recall, and rebuild jitter. Below some dataset size none of that is worth it — a plain SIMD full scan is exact, needs no index, and answers instantly. So the useful question isn't "brute force or HNSW?" but **"how many vectors can brute force serve inside my latency budget?"** Everything past that line is where HNSW earns its keep.

There are **two ceilings, not one.** Below ~200 ms you're compute-bound (latency linear in N). Past a point you hit the **RAM wall** — the vectors simply have to fit: fp32 768-dim tops out at ~2.6M in 8 GiB, and no latency budget buys you more. That wall is the hard "now you need HNSW (or sharding)" line. Binary quant pushes _both_ ceilings out — ~13× on latency and ~32× on memory (768-dim BQ is 96 bytes/vector → ~83M fit in 8 GiB) — which is why quantization, not HNSW, is the first lever to reach for. Caveats: these are server-side p50 for a single query — add your network round-trip as a fixed floor (so a 1 ms _end-to-end_ SLA is unachievable over any real network). And the BQ column is a speed/capacity story with the accuracy cost still unmeasured — see below.

## How many cores? Throughput and the second bottleneck

Everything above is single-query latency. Production serves many queries at once, so the real capacity question is throughput — and this is where core count finally enters. The napkin prediction splits by workload, because the two algorithms hit different bottlenecks:

- **Brute force is memory-bandwidth-bound.** Every query reads the whole dataset, so throughput can't exceed `memory-bandwidth / bytes-per-query`, and that ceiling has no core term in it. Concurrent scans share the one memory bus, so adding cores past the handful needed to saturate it buys nothing.
- **HNSW is compute-bound.** A query touches only ~`ef · log₂N` vectors by random gather — kilobytes, not the whole dataset — so each query is independent CPU work and throughput scales ~linearly with cores: `≈ cores / single-query-latency`.

The curves diverge exactly as the bottleneck split predicts. **Brute force peaks at p=1 (39 q/s) and falls** — one 1M scan saturates the memory bus (host CPU pinned at 97% from the first query), so extra concurrency only thrashes it. **HNSW climbs from 204 to 274 q/s** as concurrency fills the cores (CPU 87% → 99%): each query touches kilobytes, not the whole dataset, so independent queries pack onto the cores instead of fighting over the bus. On identical data that's a **7× throughput ceiling** (up to ~13× at matched concurrency), on top of a **6.6× lower single-query latency** (4.6 ms vs 30.5 ms).

And the napkin core-prediction lands: HNSW throughput ≈ `cores / query-latency` = `2 / 4.6 ms ≈ 433 q/s` ideal, measured 274 — **63% of it**, the rest lost to the co-located client stealing a core (the same ~63% efficiency the brute-force _bandwidth_ prediction hit above).

**Rule of thumb (throughput).** Brute-force throughput is set by memory bandwidth and barely moves with cores — serve at concurrency ≈ core count, expect `≈ 0.6 × (bandwidth / dataset-bytes-per-query)`, and raise it only with a fatter memory bus, not more cores on the same one. **HNSW throughput scales with cores** — `≈ 0.6 × cores / query-latency` — because queries are independent compute, until the graph's random-gather traffic eventually saturates the bus (a much higher ceiling). For **both**, single-query latency is core-independent: a query is one core's serial work, so cores buy throughput and trim tail latency under load, never single-query speed. The one thing a 2-core box can't show directly is the linear-in-cores slope — that needs a multi-core resize, the next run once the cloud cluster's key is back.

## What napkin math got right, and what I'd measure next

Two of the four curves collapse to a single constant with R² > 0.999: brute-force scan at 3.7×10⁻⁴ ms per vector (256-dim), and the HNSW build at 4.3×10⁻⁵ s per `N log₂ N`. With those two numbers you can predict this node on a dataset you haven't loaded yet, which is the whole reason to do the exercise.

The three places the numbers stop cooperating are the ones worth another run:

- **fp32 brute force above 2M.** 5M measured slower than 10M, reproducibly. Repeat each point, sweep `-p`, and pin scan parallelism so latency tracks data size instead of the scheduler.
- **Recall under binary quantization.** Every BQ number above is a speedup with no accuracy cost attached to it, which makes a 32× storage cut look free. It isn't, and I don't yet know the price.
- **HNSW search vs `log N`.** A log-N fit only reaches R² ≈ 0.7 over 100k–10M because fixed overhead swamps the signal. That needs a wider range of N, not a better fit.
