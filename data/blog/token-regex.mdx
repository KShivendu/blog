In [Token Search](/blog/token-search) I ran BM25 over BPE token IDs and it matched a Porter-stemmed English analyzer. If an engine already keeps those token postings for ranking, can the same index answer a regex like `/get_us.*config/`, or does it need a second one?

It almost can. One extra posting list finishes the job. On 45,283 Python functions the result hands the regex engine exactly the files a trigram index would. A check that only tokens allow then makes it tighter and faster than trigram: 16% fewer wrong files, and 35.3 µs per query against 50.7 µs. The whole index for ranking, regex and typos also comes out smaller than what Lucene-style engines build for the same features.

Every regex prefilter works the same way. Chop the text into pieces and remember which files each piece is in. Then chop the query the same way, keep the files that hold all its pieces, and run the real regex on those. Try your own search on 24 real functions:

## Search text falls across token cuts

A prefilter may hand the regex extra files, but it must never drop a file that matches.

The obvious move is to tokenize the query and look its tokens up. That fails because BPE tokenizes the same text differently depending on what surrounds it. The query `get_user` starts with the token `get`, but in `def get_user(` the file has `·get`, with the space inside the token. Those are two different tokens.

So the index gets asked about **chunks** instead: every 3-character window of the text any match must contain, which is what a trigram index stores. The opening regex `get_us.*config` needs `get`, `et_`, `t_u` and `_us`, then `con`, `onf`, `nfi` and `fig`, because `.*` can match anything in between. `https?://` needs `http` and `://` but never `https://`, because the `s` is optional.

A chunk inside one token is easy. A small table built from the tokenizer's vocabulary lists the tokens that contain it (`hil` is in `while`, `hill`, `child`...), and those tokens' BM25 lists already say which files hold it. The table depends only on the vocabulary (50,257 tokens for GPT-2), so it stays the same size however big the corpus grows.

A chunk that crosses the cut between two tokens is the problem. GPT-2 splits `datestamp` into `dat` and `estamp`, so search for `test`:

```
  d a t e s t a m p
  [dat  ][estamp  ]
      ^^^^
      "tes" crosses the cut, no single token holds it
```

No vocabulary lookup finds `tes` in this file. This happens a lot. In a prototype over 4,000 English words (with `o200k_base`), 28.0% of chunks crossed a cut.

## Boundary grams: store only what crosses a cut

So at every cut between two tokens, I store the 3-byte chunks that cross it, as ordinary posting lists. I call them #[boundary grams](3-byte pieces of text that straddle the cut between two tokens, stored with the list of files they appear in). `dat|estamp` stores `ate` and `tes`. Every chunk now has an answer:

```
  chunk inside a token  ->  vocabulary table -> tokens' BM25 lists
  chunk across a cut    ->  its boundary-gram list
```

The line gives 9 GPT-2 tokens, which BM25 already stores, plus 13 boundary grams, where a trigram index stores 24 chunks. Across the corpus that is **11.6M added postings** against 18.1M for a trigram index built from scratch.

Now the interesting part. A token is a run of real bytes, so it has to agree with the query everywhere they overlap. Search for `hill`: `hil` sits inside `while`, but there it is followed by `e`, and the query needs `l`. So `while` can't be part of a match, and its files can be skipped. I call this #[fitting](keeping only the tokens that agree with the query on every byte they share). It costs no storage, and a trigram index can't do it, because a trigram posting carries no token to check.

## Results

I tested on 45,283 Python functions from [CodeSearchNet](https://github.com/github/CodeSearchNet). The queries are 299 greps that coding agents really ran, taken from published [OpenHands](https://huggingface.co/datasets/nebius/SWE-rebench-openhands-trajectories) and [SWE-agent](https://huggingface.co/datasets/nebius/SWE-agent-trajectories) runs, like `GetEdk2RelativePathFromAbsolutePath`, `duckdb|DuckDB` and `get_value`. Ground truth is the regex over every file, and every method returned every true match on every query.

| method                                                                                |          postings | files handed to the regex | wrong files, total |   query p50 |
| ------------------------------------------------------------------------------------- | ----------------: | ------------------------: | -----------------: | ----------: |
| scan every file                                                                       |                   |                      100% |                    |    4,863 µs |
| dense trigram                                                                         |             18.1M |                     4.68% |             87,815 |     50.7 µs |
| [TopK sparse grams](https://www.topk.io/blog/20260814-fast-regex-search-sparse-grams) |             40.8M |                     4.60% |                    |             |
| BM25 tokens + boundary grams                                                          | 16.2M (11.6M new) |                     4.68% |             87,815 |     51.0 µs |
| + fitting, checked per query                                                          |                   |                     4.56% |             71,594 |      257 µs |
| + fitting, precomputed                                                                |                   |                     4.57% |             73,862 | **35.3 µs** |

Observations:

- **Boundary grams tie trigram exactly**, file for file, because both answer "does this file contain this chunk" and only the storage differs.
- **Fitting cuts wrong files by 16 to 18%.** `hill` goes from 913 files to 17, all true matches, and `completer` from 741 to 107 (23 true).
- **Precomputed fitting is the fastest.** When the index loads (0.42 s, nothing extra on disk), it stores the fitting lists for each chunk plus the query byte just before or after it. That keeps 86% of the gain: 73,862 wrong files against 71,594 for the full check and 87,815 without.
- **Fitting gets close to what positions buy, without storing any.** [Zoekt](https://github.com/sourcegraph/zoekt) (Sourcegraph's code search) stores trigram positions for this kind of check. On 137 case-insensitive [gitleaks](https://github.com/gitleaks/gitleaks) rules, fitting leaves 15.2 wrong files on average against 23.1 for Zoekt. On `(?i)codecov`, plain trigrams read 21 files with no match, and fitting reads 1.
- **Sparse grams hand over 0.08 points fewer files for 2.3x the postings** of a trigram index.

Posting counts hide how well lists compress, so I also wrote everything as single-segment [Tantivy](https://github.com/quickwit-oss/tantivy) indexes (a Lucene-style engine) and measured the files on disk. The fair comparison is the whole stack for BM25 ranking, case-sensitive regex, substring and typo search. Lucene-style means word postings with positions plus a lowercased trigram index, the one behind Elasticsearch's `wildcard` field. Ours is BM25 tokens, boundary grams and a sub-word dictionary for typos (explained in the side notes below). Stored text is left out of both.

Observations:

- **Ours is smaller on all three.** It comes in 17% smaller on code, 21% on news and 3% on logs.
- **The regex part alone is 13.5 MB against 17.0 MB** on code, and it keeps case. The lowercased index puts `PARAMETER` in the same list as `parameter`, so that search goes from 46 files to 7,779.
- **The chart leaves out a cost only Lucene-style pays.** Elasticsearch's `wildcard` field keeps a second copy of every value to re-check matches, where ours re-checks against the text the engine stores anyway. On code the text is 50 MB, or 21.2 MB compressed with LZ4 in 16 KB blocks. I haven't measured Elasticsearch's own copy, but at that size the Lucene-style stack would be about 51 MB against our 24.9 MB.
- **The typo part is more accurate too.** On 400 real misspellings, Lucene-style fuzzy search misses 20% of the files with the wanted word, because words like `valid` hide inside `invalid`. The sub-word dictionary misses none and keeps 0.8% of the corpus (details in the side notes below).
- **Logs are close because their tokens are short.** GPT-2 cuts `2017-05-16 00:00:01.813` into `2017|-|05|-|16| 00|:|00|:|01|.|8|13`, and every cut stores boundary grams.

A trigram index builds in 1.6 s and the token index took 9.1 s, of which 5.2 s was tokenizing with HuggingFace `tokenizers` 0.22. Its 1.0 release candidate produces identical tokens and was 30x faster in a back-to-back run, and a BM25 index pays for tokenizing anyway. I haven't timed the boundary grams on their own.

Any tokenizer that gives back the exact text works. GPT-2, Qwen3-Embedding and ISBPE hand over the same files on every query, and only the size changes: Qwen3 stores the fewest postings, 14.9M against 16.2M for GPT-2, because it merges runs of indentation. So an embedding model's own tokenizer can drive BM25 and regex from one set of token IDs. WordPiece and SentencePiece can't, since they failed all 400 code files I round-tripped (WordPiece turns `def get_vid_from_url` into `def get _ vid _ url`). That rules out the BERT-family embedding models.

## The queries matter more than the index

Some regexes have no text of 3 characters or more to look up, so every index has to read every file:

```
  no usable text                 has some
  '\s+'                          'magnet'        -> magnet
  '(.)([A-Z][a-z]+)'             'https?://'     -> http, ://
  '>(.+)<'                       'page=[0-9]+'   -> page=
```

Regexes written into source code (`re.compile` and friends) are mostly the left kind. Agent greps are mostly the right kind.

- **65.9% of the source-code regexes have no usable text, against 3.3% of agent greps** (189 of 287 against 10 of 299, the most frequent patterns of each). - **The 65.9% overstates the loss.** 28 of the 40 most common unusable patterns match at least half of a 5,000-function sample anyway (`\s+` matches every function in the sample), so no filter could skip much there.
- **Ten unfilterable greps still cost 40% of the speedup.** Greps like `HW[0-9]` and `::` read all 45,283 files. On the other 289 greps trigram runs 19.3x faster than a scan and boundary grams with fitting 22.7x.
- **A search box that shows 10 results avoids most of this.** An unfilterable regex usually matches many files, so it finds its first 10 fast. `.*/` matches 11,214 files, and the first 10 turn up after checking 12. With text stored compressed, total time over the source-code regexes drops 5.3x.
- **Top-k can't help a regex with few matches.** `HW[0-9]` matches nothing and still reads every file.

## When you need phrases

Boundary grams are loose on phrases. On 120,000 AG News articles, `be the` hands over 4,459 articles and 624 really contain it. The chunks `be ` and `e t` cross the cut between the two words, where fitting can't help, and ` the` is in most articles anyway. Two other ways to store a cut fix this for more space:

- **4-byte windows** store one key per cut, the 2 bytes on each side (`dat|estamp` stores `at|es`).
- **Token pairs** store which two tokens touch (` be` + ` the`), plus #[short-token grams](3-byte pieces that span a whole one-byte token, which a pair of tokens cannot pin down) for chunks like `t_v` in `get|_|value`.

| AG News, 360 phrases     | MB for this part | wrong files | gap to a perfect filter closed |
| ------------------------ | ---------------: | ----------: | -----------------------------: |
| boundary grams + fitting |             10.4 |      53,916 |                             6% |
| 4-byte windows + fitting |              9.6 |      21,054 |                            70% |
| token pairs + fitting    |             25.7 |       6,941 |                            98% |
| word positions (exact)   |             11.9 |           0 |                           100% |

Observations:

- **Token pairs take `be the` down to 841 articles**, but the full stack gets 27% bigger than Lucene-style on news.
- **4-byte windows are the cheap middle**, smaller than boundary grams on news. On code they cost 13% more.
- **On code all three sit within 5%**, because most agent greps are single identifiers. They leave 71,594, 68,994 and 68,112 wrong files, and a perfect filter leaves 66,819.
- **Pairs also pay when a wrong file is expensive to check.** With text stored LZ4-compressed as Lucene stores it, average queries get 7-10% faster on code and 15-25% on news. The median gets slower, 282 µs against 206 µs on code.
- **For phrases alone, positions are exact at about the same size.** They can't do substrings or regex, which is the whole point here.

My rule: boundary grams with fitting by default, 4-byte windows for prose, and token pairs only when phrases must be near-exact.

<summary>Typos, prefix search and highlights</summary>

A sub-word dictionary holds the snake_case and camelCase parts of every identifier (`get_config` gives `get` and `config`), 55,363 terms on code. Matching a typo against substrings of those parts finds the file with the wanted word every time. I tested 400 real misspellings from [codespell](https://github.com/codespell-project/codespell), like `igonore -> ignore`:

| method                                     | files kept, p50 | share of corpus | wanted files missed |
| ------------------------------------------ | --------------: | --------------: | ------------------: |
| most chunks present                        |           1,256 |            8.8% |                  0% |
| whole-term fuzzy (Lucene FuzzyQuery style) |              34 |            0.6% |                 20% |
| sub-word dictionary, substring match       |              40 |            0.8% |              **0%** |

Whole-term fuzzy misses the word when it hides inside a longer one: `valid` in `invalid`, `categories` in `subcategories`, and the real typo `useful` in `usefull`.

The same dictionary, sorted, answers prefix and suffix searches exactly. `optimi*` is one range of the sorted list: 16 parts like `optimize`, `optimization` and `optimizer`, found in 383 files. `*Error` is one range of a reversed copy. On 420 such queries its median was 600x to 2,400x faster than the chunk index plus a check. Two-letter prefixes are its weak spot, since `me*` has to merge 330 terms.

Highlights come free. The regex check already runs on every candidate file, and the span it matches is the highlight.

</details>

<details>
<summary>How it compares to Zoekt and Elasticsearch</summary>

Zoekt stores trigrams with positions and a copy of the content, and for a literal it checks only the two rarest trigrams.

- **It reads more on literals.** `su(pam_unix)[16663` matches 2 log lines. Trigrams read 2, Zoekt reads 172. On the agent greps it reads 5.14% of files against 4.68%.
- **It reads everything on some alternations.** For the GitHub-token rule `(?:ghu|ghs)_[0-9a-zA-Z]{36}` it reads all 10,000 files and we read 0.
- **Both reach a p90 of 10 wrong files on case-insensitive rules.** Positions are what get Zoekt there, and `(?i)codecov` has 128 spellings to check.
- **It stores a lot more.** A shard is 140.9 MB for 50 MB of code.

Elasticsearch's `regexp` query walks the term dictionary, so it only matches within one word: `et_use` or `def get_user` can never match. Its `wildcard` field adds the lowercased trigram index from the storage chart plus the second copy of every value mentioned there.

</details>

<details>
<summary>Three bugs the recall check caught</summary>

Each produced a believable number.

- **`"" in "?*"` is `True` in Python**, so my first extractor dropped the last character of every literal. `magnet` was searched as `magne`.
- **Treating a missing chunk as "no constraint"** turned filtered queries into full scans, and the baselines looked 5x worse than the token index (18.7% of queries scanned against 3.7%).
- **`names[0]` tokenizes as `names|[|0|]`**, so the chunk `[0]` crosses two cuts. My prototype built boundary grams from token pairs and lost it: `names\[0\]` returned 0 of 7 matching files. Walking the token stream fixed it.

</details>

## Limitations

- **Ranking on code is unmeasured.** Token BM25 matched word BM25 on prose in [Token Search](/blog/token-search).
- **Some logs come out bigger than trigram.** Tokens plus boundary grams hold more postings than a plain trigram index on 5 of 16 [Loghub](https://github.com/logpai/loghub) systems, up to 113%. BGL, HDFS and OpenStack are among them.
- **Every size uses GPT-2.** Other tokenizers give the same files at a different size.
- **No human query log.** The agent greps are real, but I have no record of what people type into code search.

## Key Takeaways

- **BM25 token postings plus boundary grams make a regex filter that ties a trigram index**, 4.68% of files either way, from 11.6M added postings against 18.1M built from scratch.
- **Fitting makes it tighter and faster than trigram.** `hill` drops from 913 files to 17, wrong files fall 16%, and the median query takes 35.3 µs against 50.7 µs. On case-insensitive rules it beats Zoekt's positions on average, 15.2 wrong files against 23.1.
- **The full stack is smaller and misses fewer typos.** Ranking, regex and typos take 24.9 MB on code against 30.1 MB for the Lucene-style equivalent, before its second copy of the text. Its typo search misses 0% of wanted files against 20%.
- **Queries with no usable text decide regex speed more than the index does**, 65.9% of source-code regexes against 3.3% of agent greps.
