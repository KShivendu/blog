Some words are more important than others in a search query. Keyword search with BM25 doesn't really understand language, so it has to guess which ones. It treats rarity as a proxy for importance, so rare words get more weight. It also drops common words like `the`, `to` and `not` using a fixed stopword list.

Rarity is a useful guess, but it can be wrong. Take `who sings she's like the wind lyrics` from [NQ](https://huggingface.co/datasets/BeIR/nq), a search over 2.68 million Wikipedia passages. `lyrics` is rare, so BM25 gives it the highest weight, 5.14. `like` is common, so it gets the lowest, 2.97. But the right passage is about the song "She's Like the Wind". It contains `like` and never says `lyrics`.

> Looking for TL;DR? Check [key takeaways](#key-takeaways)

I asked [Jev](https://openrouter.ai/docs/guides/community/jev), TypeSafe's decision model, one question about each word of the query. Its answer is a probability. That probability fits into the derivation of IDF, the word weight in BM25 and TF-IDF, so the new word weight comes out of the math with no extra knob. On held-out queries from the full NQ, FiQA and DBPedia test sets, it beats tuned BM25 on all three.

## Ask Jev about each word

Take "In which city was the former Dutch queen Juliana buried?". It comes from [DBPedia-entity](https://huggingface.co/datasets/BeIR/dbpedia-entity), a search over 4.6 million Wikipedia abstracts, and the right answer is the abstract of Juliana of the Netherlands.

[BM25](https://en.wikipedia.org/wiki/Okapi_BM25) weights each word by its rarity, called inverse document frequency or IDF. With `all` as the share of all documents that contain the word, IDF is `ln(1 / all)`. `juliana` appears in about 420 abstracts and gets 9.30. `which` appears in about 448,000 and gets 2.34.

I send Jev the whole query as context, with one question per word. All the questions for a query go in a single API request. For `dutch`, the question is:

```python
# Jev decision request, shown for the word "dutch"
state = {"search_query": "In which city was the former Dutch queen Juliana buried?"}

question = {
    "type": "score",
    "instructions": (
        'The state is a user search query. Does a document containing the word "dutch" '
        "(or a form of it, like a plural) become more likely to answer this query?"
    ),
    "criteria": [
        "Irrelevant: no, it is just as common in documents that don't answer",
        "Essential: yes, every document that answers the query contains it",
    ],
}
```

Jev returns a probability for each label, and the two add up to 1. I keep the probability of Essential and call it `jev`. Jev gives `juliana` 93% and `which` 18%.

## Turn the answer into a word weight

IDF comes from the [relevance weight](https://doi.org/10.1002/asi.4630270302) of Robertson and Spärck Jones. It compares two odds: that a right document (one that answers the query) contains the word, and that any document does. BM25 doesn't know the first odds, so [Croft and Harper](https://doi.org/10.1108/eb026683) assumed a coin flip: half the right documents contain the word. A coin flip has odds of 1. Lucene adds 1 inside the log so the weight is never negative, and that gives BM25's IDF:

```
# BM25's IDF, with the coin flip's odds written out
IDF = ln(1 + 1 × (1 − all) / all)  =  ln(1 / all)
```

Jev replaces that 1 with its own odds, `jev / (1 − jev)`. Here is the weight for `dutch`. About 32,700 of the 4.6 million abstracts contain it, and Jev is 88% sure it is Essential:

```
# Word weight for "dutch" in DBPedia
all        = 32,700 / 4.6 million                       = 0.00706
(1 − all) / all                                         = 140.6
coin flip:  odds 1                  → ln(1 + 1    × 140.6) = 4.95   (BM25's IDF)
Jev:        odds 0.88 / 0.12 = 7.33 → ln(1 + 7.33 × 140.6) = 6.94
```

Here is the change in the formula. `df` counts documents containing the word, `N` is the total documents, and `jev` is Jev's probability of Essential:

<div className="jev-formula" tabIndex={0} aria-label="Word weight before and after adding Jev">

$$
\begin{aligned}
\text{all} &= \frac{\mathrm{df}+0.5}{N+1} \\
\text{BM25 weight} &= \mathrm{IDF} = \ln\!\left(1 + 1 \cdot \frac{1-\text{all}}{\text{all}}\right) \\
\text{With Jev} &= \ln\!\left(1 + \frac{\text{jev}}{1-\text{jev}} \cdot \frac{1-\text{all}}{\text{all}}\right)
\end{aligned}
$$

</div>

Here is the whole query:

| Word    | `jev` | BM25 IDF | BM25 + Jev |
| ------- | ----: | -------: | ---------: |
| juliana |   93% |     9.30 |      11.89 |
| buried  |   91% |     6.59 |       8.90 |
| queen   |   90% |     5.19 |       7.39 |
| dutch   |   88% |     4.95 |       6.94 |
| city    |   69% |     2.91 |       3.68 |
| former  |   48% |     2.91 |       2.83 |
| which   |   18% |     2.34 |   **1.11** |

- At `jev = 50%` Jev's odds are 1, so the weight is exactly BM25's IDF. `former` gets 48% and barely moves, from 2.91 to 2.83.
- Above 50% the weight rises, and below 50% it falls. `which` isn't on the stopword list, and Jev drops it to half its IDF.
- At `jev = 0` the weight is 0, and it is never negative. Jev's answers stay between 1% and 99%, so there is nothing to clip or tune.

Rarity and Jev's answer are two separate signals, so every word lands in one of four boxes. Each cell shows BM25's IDF → the weight with Jev:

|                 | Jev says Irrelevant | Jev says Essential     |
| --------------- | ------------------- | ---------------------- |
| **Rare word**   | `give` 5.55 → 2.68  | `juliana` 9.30 → 11.89 |
| **Common word** | `which` 2.34 → 1.11 | `high` 2.41 → **3.86** |

- `juliana` is rare and Essential, so it was already heavy and gets heavier.
- `high` in "What is considered high or low when talking about volume?" is common on a finance forum, so BM25 gives it little weight. Jev gives it 82%, and its weight rises by **60%**.
- `give` in "Give me all presidents of the United States." is rare in Wikipedia, so BM25 trusts it. Jev gives it 5%, and its weight halves. `presidents` rises from 4.19 to 7.65.
- `which` is common and Irrelevant, so it falls to half its IDF.

BM25 can only tell the two rows apart. Jev adds the two columns.

The weight only replaces IDF. BM25's term frequency and length normalization stay the same, with its usual #[k₁ and b](BM25 settings for how fast repeated words stop adding score and how much long documents are penalised).

## Does it improve search?

I ran the full test sets of three datasets from [BEIR](https://github.com/beir-cellar/beir):

- [NQ](https://ai.google.com/research/NaturalQuestions): 3,452 Google questions against 2.68 million Wikipedia passages.
- [FiQA](https://sites.google.com/view/fiqa/): 648 questions from a personal finance forum against 57,638 posts.
- [DBPedia-entity](https://huggingface.co/datasets/BeIR/dbpedia-entity): 400 entity queries against 4.6 million Wikipedia abstracts.

Both methods use the same stemming and stopwords. I tuned `k₁` and `b` for each method on a random half of each dataset's queries, trying 25 settings. The other half is what I score: 1,726 NQ, 324 FiQA and 200 DBPedia queries. Jev adds no setting of its own, so both methods get the same 25 tries.

Jev only sees the query. It never sees the documents or the relevance labels. I picked the question's wording on 120 of the 2,250 scored queries, 40 from each dataset. Without those 120, Jev still gains on all three: NQ +2.74, FiQA +1.25 and DBPedia +1.08, each with its 95% interval above 0.

Observations:

- "what is the female lion called in lion king" rises from 0 to 100 on NQ.
- NQ's median rises from 20.44 to **28.91**, more than its mean, which goes from 30.54 to 33.37.
- "What is considered high or low when talking about volume?" rises from 38.69 to 80.66 on FiQA. The Juliana query rises from 63.09 to 100 on DBPedia.
- Some queries get worse. "who painted the world famous painting the last supper" falls from 100 to 38.69 on NQ. On FiQA, "Why big clients want the contractor to be incorporated before giving them work" falls from 100 to 63.09. On DBPedia, "Seoul Korea river name ethnic group China" falls from 33.92 to 0.
- p25 is 0 on NQ and FiQA for both methods, because more than a quarter of those queries find no relevant document in the top 10.

There is [no free lunch in search evals](/blog/stop-averaging-evals#which-queries-moved). Any kind of change helps some queries and hurts others. Jev helps more queries than it hurts on every dataset:

| Dataset | Better / worse / same | Mean gain, #[95% bootstrap interval](range of the mean gain over 5,000 resamples of the queries) |
| ------- | --------------------: | -----------------------------------------------------------------------------------------------: |
| NQ      |     332 / 113 / 1,281 |                                                                       **+2.83** (+2.28 to +3.38) |
| FiQA    |         69 / 42 / 213 |                                                                           +1.86 (+0.71 to +3.10) |
| DBPedia |          70 / 39 / 91 |                                                                           +1.63 (+0.63 to +2.66) |

A #[sign test](how likely this many more wins than losses would be if each change were a coin flip) puts the chance of this being luck below 1 in 50 on every dataset.

Simpler mixes also beat tuned BM25. Mean nDCG@10 on the same scored queries:

| Word weight                                            |    NQ |  FiQA | DBPedia |
| ------------------------------------------------------ | ----: | ----: | ------: |
| Tuned BM25: `IDF`                                      | 30.54 | 25.65 |   40.17 |
| This post: `ln(1 + jev / (1 − jev) × (1 − all) / all)` | 33.37 | 27.51 |   41.80 |
| `IDF × jev`                                            | 33.78 | 28.18 |   42.45 |
| `IDF + c × ln(jev / (1 − jev))`, `c` tuned per dataset | 34.59 | 27.58 |   42.62 |

Every form beats BM25 on all three datasets, so the gain comes from Jev's answers rather than from one formula. The other two score a little higher, but `IDF × jev` has no derivation behind it, and `c` is one more setting to tune for each dataset. The weight in this post follows from the relevance weight and has nothing to tune.

</details>

## Cost and latency

Jev answers all the questions for a query in one API request. Fetching the answers for all 3,452 NQ queries cost \$0.16, about **\$0.05 per 1,000 queries**. The price grows with query length. 200 HotpotQA queries, 16 words each on average, cost \$0.07 per 1,000.

Latency matters more than price. I timed those 200 HotpotQA queries, one request at a time:

| Jev request |    p50 |      p95 |      p99 |
| ----------- | -----: | -------: | -------: |
| Time        | 763 ms | 1,179 ms | 1,338 ms |

BM25 itself answers in a few milliseconds, so the Jev call sets the query time. Jev's job here is small: one probability per query word. A tiny model distilled from Jev's answers could run next to the index in a few milliseconds, at almost no cost per query.

## What's next

- **Distill Jev.** Train a tiny model on Jev's answers for millions of queries. That removes the API call, its 763 ms and its price.
- **Ask Jev about documents too.** The same idea works at index time: ask once per document and word, 'Does it discuss "langchain"?', and store the answer in the index. It adds no query-time cost. In an early test on the LangChain questions of [FreshStack](https://fresh-stack.github.io/), a benchmark of technical questions answered from code docs, it lifted BM25 + Jev from 17.16 to 19.97 nDCG@10. That test only re-scored each query's top 20 results, so a full index run is still to come.

## Key Takeaways

- With `k₁` and `b` tuned for both methods, mean nDCG@10 rises on all three datasets: NQ **30.54 → 33.37**, FiQA 25.65 → 27.51 and DBPedia 40.17 → 41.80.
- Ask Jev one question per query word: does a document containing it become more likely to answer? Its odds `jev / (1 − jev)` replace the coin flip inside IDF: `ln(1 + jev / (1 − jev) × (1 − all) / all)`, where `all` is the share of documents containing the word.
- There is no new knob. At `jev = 50%` the weight is exactly BM25's IDF, and Jev raises the words it is sure about and lowers the ones it isn't.
