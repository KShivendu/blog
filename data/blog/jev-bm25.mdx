Some words are more important than others in a search query. Keyword search with BM25 doesn't really understand language, so it has to guess which ones. It treats rarity as a proxy for importance, so rare words get more weight. It also drops common words like `the`, `to` and `not` using a fixed stopword list.

Rarity is a useful guess, but it can be wrong. Take `who sings she's like the wind lyrics` from [NQ](https://huggingface.co/datasets/BeIR/nq), a search over 2.68 million Wikipedia passages. `lyrics` is rare, so BM25 gives it the highest weight, 5.14. `like` is common, so it gets the lowest, 2.97. But the right passage is about the song "She's Like the Wind". It contains `like` and never says `lyrics`.

> Looking for TL;DR? Check [key takeaways](#key-takeaways)

I asked [Jev](https://openrouter.ai/docs/guides/community/jev), TypeSafe's decision model, one question about each word of the query. Its answer is a probability. That probability fits into the derivation of IDF, the word weight in BM25 and TF-IDF, so the new word weight comes out of the math with no extra knob. On held-out queries from the full NQ, FiQA and DBPedia test sets, it beats tuned BM25 on all three.

## Ask Jev about each word

Take "In which city was the former Dutch queen Juliana buried?". It comes from [DBPedia-entity](https://huggingface.co/datasets/BeIR/dbpedia-entity), a search over 4.6 million Wikipedia abstracts, and the right answer is the abstract of Juliana of the Netherlands.

[BM25](https://en.wikipedia.org/wiki/Okapi_BM25) weights each word by its rarity, called inverse document frequency or IDF. A rare word picks out a few documents from the rest, so matching it counts for more. IDF is the log of the word's rarity: `juliana` shows up in 1 of every 10,950 abstracts, so it gets ln 10,950 = 9.30. `which` shows up in 1 of every 10, so it gets only 2.34.

I send Jev the whole query as context, with one question per word. All the questions for a query go in a single API request. For `dutch`, the question is:

```python
# Jev decision request, shown for the word "dutch"
state = {"search_query": "In which city was the former Dutch queen Juliana buried?"}

question = {
    "type": "score",
    "instructions": (
        "The state is a user search query. For telling documents that answer this query apart "
        'from documents that do not, is the word "dutch" (or a form of it, like a plural) '
        "a signal or noise?"
    ),
    "criteria": [
        "Noise: answering and non-answering documents contain it equally often",
        "Signal: every answering document contains it",
    ],
}
```

Jev returns a probability for each label, and the two add up to 1. I call the probability of signal `jev`. Jev gives `juliana` 97% and `which` 8%.

## Turn the answer into a word weight

Signal gets `jev` and noise gets `1 − jev`. I don't use `jev` as the importance directly. I use the odds of signal.

[Odds](https://en.wikipedia.org/wiki/Odds) compare the chance something happens with the chance it doesn't. A horse with an 80% chance to win and a 20% chance to lose has odds of 80 / 20 = 4, usually said as "4 to 1". At 50% the odds are 1, called even odds. A word's importance is its odds of being a signal, which is also its signal-to-noise ratio:

```
importance = P(signal) / P(noise) = jev / (1 − jev)
```

Importance 1 means even odds. Above 1 the word matters, and below 1 it doesn't. Its log is a bonus added to the word's IDF:

| Jev says signal | Importance | Bonus to IDF |
| --------------- | ---------: | -----------: |
| 95%             |         19 |         +2.9 |
| 86% (`dutch`)   |        6.1 |         +1.8 |
| 50%             |          1 |            0 |
| 8% (`which`)    |       0.09 |         −2.4 |
| 2% (`talking`)  |       0.02 |         −3.9 |

`dutch` has an IDF of 4.95. Jev says 86% signal and 14% noise, so its importance is 6.1 and its weight becomes 4.95 + 1.8 = 6.76.

Where does the bonus come from? The formula is based on the [relevance weight](https://doi.org/10.1002/asi.4630270302) that Robertson and Spärck Jones published in 1976, which is also the reasoning behind IDF. Their weight compares two groups, the right documents (the ones that answer the query) and all documents. A word matters when it shows up much more often in the first group than in the second.

Their weight needs the odds that a right document contains the word. They counted it from documents people had marked as relevant. Search engines have no such labels, so [Croft and Harper](https://doi.org/10.1108/eb026683) assumed a coin flip in 1979: half the right documents contain each word. Even odds add nothing, and the weight reduces to rarity alone, which is IDF.

This post makes two different choices:

- **Jev's odds replace the coin flip.** Nobody counts relevant documents. Jev judges from the query alone how much each word separates the right documents from the rest, and its odds of signal stand in for the counted odds.
- **The 1 stays inside the log.** Lucene's IDF adds 1 to rarity so a weight never drops below 0, and I keep that. For a rare word the result matches Robertson and Spärck Jones's weight. For a common word it softens the drop, as `which` shows below.

Here is the full formula. `N` is the number of documents and `df` is how many of them contain the word. Rarity is how many documents lack the word for each one that has it. Lucene adds 0.5 to both counts, and the 1 inside the log keeps a weight from dropping below 0. Adding 1 to rarity gives back the usual IDF, because `1 + (N − df + 0.5) / (df + 0.5) = (N + 1) / (df + 0.5)`:

<div className="jev-formula" tabIndex={0} aria-label="Word weight before and after adding Jev">

$$
\begin{aligned}
\text{rarity} &= \frac{N-\mathrm{df}+0.5}{\mathrm{df}+0.5} \\
\text{BM25 weight} &= \ln\!\left(1 + \text{rarity}\right) = \ln\frac{N+1}{\mathrm{df}+0.5} = \mathrm{IDF} \\[1.2em]
\text{importance} &= \frac{P(\text{signal})}{P(\text{noise})} = \frac{\text{jev}}{1-\text{jev}} \\
\text{With Jev} &= \ln\!\left(1 + \text{importance} \cdot \text{rarity}\right)
\end{aligned}
$$

</div>

Here it is for `dutch`:

```
# "dutch" in DBPedia: N = 4.6 million abstracts, df = 32,700, jev = 86%
rarity        = (4,600,000 − 32,700) / 32,700        ≈ 140
BM25 weight   = ln(1 + 140) = ln(4,600,001 / 32,700.5) = 4.95
importance    = 0.86 / 0.14                          ≈ 6.1
With Jev      = ln(1 + 6.1 × 140)                    = 6.76
```

For a rare word like `dutch`, this comes out as IDF plus the bonus from the table, the log of importance. For a common word like `which`, IDF plus the bonus would go below 0 (2.34 − 2.4). The 1 inside the log stops that, and the weight lands at 0.59.

Here is the whole query:

| Word    | `jev` | BM25 IDF | BM25 + Jev |
| ------- | ----: | -------: | ---------: |
| juliana |   97% |     9.30 |      12.78 |
| buried  |   89% |     6.59 |       8.68 |
| dutch   |   86% |     4.95 |       6.76 |
| queen   |   82% |     5.19 |       6.71 |
| city    |   51% |     2.91 |       2.95 |
| former  |   25% |     2.91 |       1.91 |
| which   |    8% |     2.34 |   **0.59** |

- At `jev = 50%` the importance is 1 and the bonus is 0, so the weight is exactly BM25's IDF. `city` gets 51% and barely moves, from 2.91 to 2.95.
- Above 50% the weight rises, and below 50% it falls. `which` isn't on the stopword list, and Jev drops it to a quarter of its IDF.
- At `jev = 0` the weight is 0, and it is never negative. Jev's answers stay between 1% and 99%, so there is nothing to clip or tune.

Rarity and Jev's answer are two separate signals, so every word lands in one of four boxes. Each cell shows BM25's IDF → the weight with Jev:

|                 | Jev says noise      | Jev says signal        |
| --------------- | ------------------- | ---------------------- |
| **Rare word**   | `give` 5.55 → 1.83  | `juliana` 9.30 → 12.78 |
| **Common word** | `which` 2.34 → 0.59 | `high` 2.41 → **3.30** |

- `juliana` is rare and Jev says yes, so it was already heavy and gets heavier.
- `high` in "What is considered high or low when talking about volume?" is common on a finance forum, so BM25 gives it little weight. Jev gives it 72%, and its weight rises by **37%**.
- `give` in "Give me all presidents of the United States." is rare in Wikipedia, so BM25 trusts it. Jev gives it 2%, and its weight drops to a third. `presidents` rises from 4.19 to 7.35.
- `which` is common and Jev says noise, so it falls to a quarter of its IDF.

BM25 can only tell the two rows apart. Jev adds the two columns.

The weight only replaces IDF. BM25's term frequency and length normalization stay the same, with its usual #[k₁ and b](BM25 settings for how fast repeated words stop adding score and how much long documents are penalised).

## Does it improve search?

I ran the full test sets of three datasets from [BEIR](https://github.com/beir-cellar/beir):

- [NQ](https://ai.google.com/research/NaturalQuestions): 3,452 Google questions against 2.68 million Wikipedia passages.
- [FiQA](https://sites.google.com/view/fiqa/): 648 questions from a personal finance forum against 57,638 posts.
- [DBPedia-entity](https://huggingface.co/datasets/BeIR/dbpedia-entity): 400 entity queries against 4.6 million Wikipedia abstracts.

All methods use the same stemming and stopwords. Default BM25 uses Elasticsearch's defaults, `k₁ = 1.2` and `b = 0.75`. For tuned BM25 and BM25 + Jev, I tuned `k₁` and `b` on a random half of each dataset's queries, trying 25 settings. The other half is what I score: 1,726 NQ, 324 FiQA and 200 DBPedia queries. Jev adds no setting of its own, so both tuned methods get the same 25 tries.

Jev only sees the query. It never sees the documents or the relevance labels. I chose the question's wording by comparing about a dozen wordings, partly on these scored queries. The exact words matter little. Swapping "signal or noise" for "useful or useless" changes the mean by at most 0.11 on every dataset. A different question, 'Does a document containing the word become more likely to answer this query?', also beats tuned BM25 on all three: NQ +2.83, FiQA +1.86 and DBPedia +1.63.

Observations:

- "who sings i'm going to soak up the sun" rises from 0 to 100 on NQ.
- NQ's median rises from 20.44 to **30.10**, more than its mean, which goes from 30.55 to 33.74. With Elasticsearch's defaults, the NQ median is 0.
- "Tax question about selling a car" rises from 0 to 63.09 on FiQA. The Juliana query rises from 63.09 to 100 on DBPedia.
- Jev cuts the zero rate on every dataset. On NQ, it finds something relevant for 89 queries where tuned BM25 found nothing, and loses it on 26.
- Some queries get worse. "who painted the world famous painting the last supper" falls from 100 to 43.07 on NQ. On FiQA, "Why big clients want the contractor to be incorporated before giving them work" falls from 100 to 50. On DBPedia, "Seoul Korea river name ethnic group China" falls from 33.92 to 0.
- p25 is 0 on NQ and FiQA for every method, because almost half of those queries find no relevant document in the top 10.

There is [no free lunch in search evals](/blog/stop-averaging-evals#which-queries-moved). Any kind of change helps some queries and hurts others. Jev helps more queries than it hurts on every dataset:

| Dataset | Better / worse / same | Mean gain, #[95% bootstrap interval](range of the mean gain over 5,000 resamples of the queries) |
| ------- | --------------------: | -----------------------------------------------------------------------------------------------: |
| NQ      |     358 / 153 / 1,215 |                                                                       **+3.19** (+2.52 to +3.84) |
| FiQA    |         88 / 35 / 201 |                                                                           +2.89 (+1.55 to +4.30) |
| DBPedia |          77 / 36 / 87 |                                                                           +2.02 (+0.96 to +3.10) |

A #[sign test](how likely this many more wins than losses would be if each change were a coin flip) puts the chance of this being luck below 1 in 5,000 on every dataset.

## Cost and latency

Jev answers all the questions for a query in one API request. Fetching the answers for all 3,452 NQ queries cost \$0.15, about **\$0.05 per 1,000 queries**. The price grows with query length. 200 HotpotQA queries, 16 words each on average, cost \$0.07 per 1,000.

Latency matters more than price. I timed those 200 HotpotQA queries, one request at a time:

| Jev request |    p50 |      p95 |      p99 |
| ----------- | -----: | -------: | -------: |
| Time        | 763 ms | 1,179 ms | 1,338 ms |

BM25 itself answers in a few milliseconds, so the Jev call sets the query time. Jev's job here is small: one probability per query word. A tiny model distilled from Jev's answers could run next to the index in a few milliseconds, at almost no cost per query.

## What's next

- **Find the best formula.** How Jev's answer turns into a weight matters. Simpler mixes, like `IDF × jev`, also beat tuned BM25, and some do better on one dataset and worse on another. I'll keep testing forms that stay as clean as this one.
- **Distill Jev.** A tiny model trained on Jev's answers removes the API call and its price. A first 2-layer student, trained on Jev's answers for 22,000 MS MARCO queries, runs in 3.2 ms per query instead of about 500 ms. On [NanoBEIR](https://huggingface.co/collections/zeta-alpha-ai/nanobeir-66e1a0af21dfd93e620cd9f6) it lifts tuned BM25 from 59.79 to 60.40 nDCG@10, while Jev itself reaches 61.51. That test used an earlier prompt and formula, so the next step is to train on far more queries with this post's prompt.
- **Ask Jev about documents too.** The same idea works at index time: ask once per document and word, 'Does it discuss "langchain"?', and store the answer in the index. It adds no query-time cost. In an early test on the LangChain questions of [FreshStack](https://fresh-stack.github.io/), a benchmark of technical questions answered from code docs, it lifted BM25 + Jev from 17.16 to 19.97 nDCG@10. That test only re-scored each query's top 20 results, so a full index run is still to come.

## Key Takeaways

- With `k₁` and `b` tuned for both methods, mean nDCG@10 rises on all three datasets: NQ **30.55 → 33.74**, FiQA 25.65 → 28.54 and DBPedia 40.31 → 42.33. Elasticsearch's default BM25 scores 28.96, 25.65 and 38.18.
- Ask Jev one question per query word: is it a signal or noise for telling answering documents apart? A word's importance is its signal-to-noise ratio, P(signal) / P(noise). The weight is `ln(1 + importance × rarity)`, and BM25's IDF is the same formula with every importance set to 1.
- There is no new knob. At `jev = 50%` the weight is exactly BM25's IDF, and Jev raises the words it is sure about and lowers the ones it isn't.
