> Looking for TL;DR? Check [key takeaways](#key-takeaways)

In [Token Search](/blog/token-search) I ran BM25 over BPE token IDs and it matched a Porter-stemmed English analyzer. Those postings are keyed by token ID, and a token covers about four bytes where a character gram covers half of one. So a fair question is whether the same index can answer `/colou?r of the (sky|sea)/` without building a second one.

It almost can. One extra posting list finishes the job, and the result ties the standard approach while beating [TopK's sparse grams](https://www.topk.io/blog/20260814-fast-regex-search-sparse-grams) on postings and build time. But the thing that decides how fast regex search feels turned out to have nothing to do with the index at all. **It is what fraction of queries contain no literal text to look up**, and that fraction depends entirely on who is typing.

Every method here does the same two things: chop the text into pieces, and remember which documents each piece appeared in. Then chop the query the same way, look its pieces up, and run the real regex on whatever survives. Watch it on 60 real documents:

## Why a token index needs help

A prefilter has one obligation. It may hand the verifier junk, but it must never drop a document that actually matches. Extra candidates cost time, a missing candidate is a wrong answer.

TopK's rule earns that. They weight character bigrams with CRC32 and select a gram when both boundary bigrams outweigh every interior one, so the choice depends only on characters inside the gram. Query and document agree without communicating.

BPE has no such property. Merges apply in rank order across the whole word, so a suffix rewrites the prefix:

```
  "in"            ->  [in]
  "ing"           ->  [ing]           the [in] is gone
  "token"         ->  [token]
  "tokenization"  ->  [token][ization]
```

A piece of a word does not tokenize to a piece of that word's tokens. Here is the same line of Python chopped three ways, with the real pieces from each method:

So the token index cannot be asked about arbitrary text directly. Instead it gets asked about **chunks**, meaning every 3-character window of a required literal, which is what a trigram index stores. `colou?r of the (sky|sea)` becomes a boolean query either way, and the two methods differ only in what the terms are:

```
  regex:  colou?r of the (sky|sea)

  TopK:   " the" AND "r of t" AND ("e se" OR "e sk")
  chunks: "the" AND "of " AND ("sky" OR "sea")
          AND ("col" AND "olo" AND "lor")
```

The gap that matters is the seam. Take `datestamp`, which BPE chops into `dat` and `estamp`, and search for `test`:

```
  d a t e s t a m p
  [dat  ][estamp  ]
      ^^^^
      test spans the cut, so no single token holds it
```

Searching the token vocabulary for a piece containing `test` finds nothing, because the word was split through the middle of it. Over a corpus of English words, **28.0% of a word's chunks sit inside no single token** and 77.6% of words have at least one such chunk. The seam is the common case.

So the design needs two lookups per chunk. Tokens whose text contains the chunk, which a 2 MB static index over the vocabulary answers, or **token pairs that spell it across a seam**, which needs one new posting list keyed by adjacent token pairs.

That second index does the heavy lifting, and cheaply, because the vocabulary permits far more pairs than reality contains:

| literal   | pairs the vocabulary allows | pairs that actually occur |  pruning |
| --------- | --------------------------: | ------------------------: | -------: |
| `ization` |                         778 |                         1 |     778x |
| `gRPC`    |                       5,636 |                         2 |   2,818x |
| `keniz`   |                      19,425 |                        29 |     670x |
| `veal`    |                     213,970 |                         1 | 213,970x |

Observations:

- **The prune is sound rather than heuristic.** The bigram index is built from the same corpus, so a pair that never occurs adjacently there cannot occur in any document of it. Nothing is dropped.
- **`veal` allows 213,970 pairs because 726 tokens end in `ve` and 292 start with `al`.** Exactly one of those combinations appears in real text.

## The benchmark needs no labels

Filter quality is candidate-set size, and ground truth is whether the regex matches, which Python computes exactly. So this needs no human judgments, unlike the NanoBEIR runs in Token Search.

- **Documents.** Python functions from [CodeSearchNet](https://github.com/github/CodeSearchNet).
- **Queries.** Regexes mined from `re.compile`, `re.search` and friends in the **train** split, so the patterns are ones developers wrote and the documents are disjoint from where they came.
- **Ground truth.** `re.search(pattern, doc)` over every pair.
- **The check that matters.** Recall must be exactly 1.000. A filter that drops a matching document is a wrong answer rather than a tuning choice.

That check caught four bugs in my own code, and two carry a lesson worth keeping.

**`"" in "?*"` is `True` in Python.** My literal extractor tested whether the next character was a quantifier, and at the end of a string the next character is the empty string, which is a substring of everything. Every literal silently lost its last character. `'magnet'` was searched as `magne`.

**The normalisation has to run at index time too.** Token Search encodes each word alone with a fixed leading space, `enc.encode(" " + word)`. I applied that to queries and left the index on raw tokenisation. For the literal `</pre>` the safe word is `pre`, the query encodes `" pre"`, but in the document `pre` follows `/` and tokenises differently, so the true match never entered the candidate set. The leading-space trick assumes words are space-delimited, and in code they mostly are not.

After the fixes, all three methods return every true match on all 400 patterns.

Observations:

- **Token postings plus the bigram index hold 2.41M postings against sparse grams' 6.51M**, a 2.7x gap that comes from one fact: a token posting covers about four bytes where a character gram covers half of one.
- **Sparse grams are 2.2x larger than the dense trigram index they improve on.** Their `E[grams] ~= 2L` counts bytes, and since selection probability at length 3 is exactly 1, every trigram is indexed and the longer grams roughly double it. Sparsity is measured against a dense index holding every length at once, so it buys selectivity rather than size.
- **Build time splits the same way**, 6.3 s for token plus bigram against 12.2 s for sparse grams and 1.1 s for dense trigrams, because gram selection walks every length from 3 to 16 at every byte position.

## Selectivity is a three-way tie

Mean percentage of the corpus handed to the verifier, by query class, so lower is better. This table uses the 4,000-document run, because that is the one where every method was checked for recall on all 400 patterns.

| class        |   n | true matches | dense trigram | TopK sparse | token + bigram |
| ------------ | --: | -----------: | ------------: | ----------: | -------------: |
| word-aligned |  59 |           30 |          0.8% |        0.8% |           0.8% |
| sub-word     | 123 |           19 |          5.8% |        5.8% |           5.8% |
| alternation  |   4 |            1 |          0.1% |        0.1% |           0.1% |
| no-literal   | 214 |        1,404 |        100.0% |      100.0% |         100.0% |

Observations:

- **Token plus bigram matches the dense trigram index to the decimal in every class.** It computes the same function from different storage, resolving "does this document contain this chunk" through the vocabulary index and token adjacency instead of storing a chunk posting list, so it lands on the same candidates.
- **Sparse grams buy nothing measurable here**, at 2.7x the postings and 1.9x the build time. Their longer grams are meant to encode adjacency, but TopK select an n-character gram with probability `2/((n-1)(n-2))`, so a 5-character literal carries its adjacency-bearing gram 1 time in 6 and otherwise falls back to plain trigrams.
- **The one place any method separates** is sub-word false positives, where sparse grams return 1.2x the true matches against 1.3x for the other two. That is one notch of the median rather than anything a user would feel.
- **The bottom row is the whole story of this post.** 214 of 400 patterns get no constraint from any method.

### The prediction that broke

Before running this I modelled `/keniz/` and predicted token plus bigram would beat sparse grams **5.2x** on sub-word literals, reasoning that `ken`, `eni` and `niz` can appear scattered through a document without being adjacent, so a trigram index admits `kennel ... genie ... organize` while adjacency forbids it. That model assumed dense trigrams return **8x** the true matches. Measured, they return **1.3x**.

The reasoning was fine and the input was wrong. The median mined sub-word literal is 6 characters, which yields 4 chunks, and ANDing 4 chunk lists is already near-exact. My 8x came from a 5-character literal in isolation, the shortest case that still clears a trigram index and so the most favourable one I could have picked. Adjacency had nothing left to remove.

## The number nobody quotes

**53.5% of these regexes must read every document, under every method.** They pin down no text of three characters or more, so no index has a key to look up:

```
  no usable literal              has one
  '\s+'                          'magnet'            -> magnet
  '\d+'                          'tower[0-9]+/'      -> tower
  '[-/]'                         'https?://'         -> http AND ://
  '(.)([A-Z][a-z]+)'             'page=[0-9]+'       -> page=
  '>(.+)<'                       '__version__ = ...' -> __version__ =
```

Note `https?://` gives `http` and `://` but never `https://`. The `s` sits under `?`, so a matching document need not contain it, and a sound filter may only require characters guaranteed present. `>(.+)<` fails for a duller reason: `>` and `<` are one character each, below the three a chunk needs.

Then I noticed those patterns are string-processing utilities rather than searches. Nobody greps a repo for `\s+`. So I pulled the searches coding agents really run, out of published [OpenHands](https://huggingface.co/datasets/nebius/SWE-rebench-openhands-trajectories) and [SWE-agent](https://huggingface.co/datasets/nebius/SWE-agent-trajectories) trajectories: 1,079 distinct patterns from 2,400 agent runs.

Observations:

- **Swapping the query set moves every index from about 2.1x to about 11.4x**, and the indexes stay tied to each other. The old ceiling was never the index, it was the half of the query set no index can help.
- **Agent queries are 96.3% filterable against 48.2% for mined `re.compile` patterns**, both at a 3-character minimum literal, because agents search for identifiers like `GetEdk2RelativePathFromAbsolutePath` where source-code regexes describe shapes like `(.)([A-Z][a-z]+)`.
- **A 3.7% fallback rate still costs half the available speedup.** The filterable slice alone reaches 24x and the aggregate lands at 11.4x, because each unfilterable query costs about 24x more than a filtered one.
- **The filterable slice reproduces TopK's setting.** Counting only queries an index can help, the speedups run 36.5x to 50.0x, the same order as their reported 55.3x, which is the external check that this benchmark and theirs describe the same slice of traffic.

The agent queries also found a bug the human ones hid. `names\[0\]` returned 0 candidates for 7 matching documents, because I derived seam chunks from the bigram index, which sees only pairs, and a chunk can span **three** tokens when the middle one is a single character. `names[0]` tokenises with `[`, `0` and `]` separate, so the chunk `[0]` belonged to no pair. Human patterns lacked the punctuation density to trigger it. Walking the token stream instead is sound for any token length.

## Does the advantage survive at scale?

Four ANDed chunks being near-exact is what makes the tie a tie, and that should weaken as the corpus grows and each chunk hits more documents. Sparse grams should start earning their length. That was my prediction, and I swept the corpus 16x on roaring bitmaps to check.

| corpus       | dense trigram | TopK sparse | sparse advantage |
| ------------ | ------------: | ----------: | ---------------: |
| 8,000 docs   |         4.91% |       4.86% |         +0.05 pp |
| 32,000 docs  |         4.98% |       4.93% |         +0.04 pp |
| 128,000 docs |         5.09% |       5.05% |         +0.04 pp |

Observations:

- **The advantage shrinks across a 16x corpus increase** rather than growing, so the prediction was wrong in direction as well as size.
- **The candidate fraction barely moves**, 4.91% to 5.09%, so four ANDed chunks stay near-exact and there is still nothing for a longer gram to remove.
- **Build cost is what scales, and it is where the token route looks worst.** At 128,000 documents:

| at 128,000 docs   |       postings |   build |     p50 |
| ----------------- | -------------: | ------: | ------: |
| dense trigram     |     50,246,591 |  19.2 s | 0.25 ms |
| TopK sparse grams |    112,362,219 | 211.1 s | 0.71 ms |
| token + bigram    | **41,302,244** | 115.9 s | 0.29 ms |

The token route holds the smallest index at two orders of magnitude, and takes 6.0x longer to build than a dense trigram index. Sparse grams take 11.0x longer and hold 2.7x the postings.

## The tokenizer is a correctness decision

Everything above uses `o200k_base` because Token Search did. That was a default rather than an argument, so I tested the alternatives against the one property a filter actually needs: **the pieces have to reassemble into the original text.** If they do not, the chunks you derive belong to text no document contains.

| tokenizer                     | round-trips exactly, 400 code files |
| ----------------------------- | ----------------------------------: |
| BPE `o200k_base`              |                         **400/400** |
| WordPiece `bert-base-uncased` |                               0/400 |
| SentencePiece `xlm-roberta`   |                               0/400 |

Observations:

- **WordPiece and SentencePiece fail every document.** WordPiece turned `def get_vid_from_url` into `def get _ vid _ url` and `makeMimi` into `makemimi`, changing 47,281 characters. SentencePiece collapsed newline runs, changing 87,986. A regex for `get_vid_from_url` then derives chunks the index does not hold. Normalisation helps a language model and breaks a filter.
- **That rules both out on correctness**, whatever they do for retrieval quality.

## Typo search comes free

The chunk lookup answers "which documents contain this 3-character sequence", which is exactly what classic q-gram typo search runs on. Chop the misspelled word and require most of its chunks instead of all of them, since one edit damages at most three.

Over 3,000 documents and 322 agent query words of 6 characters or more, one synthetic edit each, with **nothing added to the index**:

```
  recall of documents holding the correct word   15,889/15,889 = 100.0%
  candidates                                     p50 242, mean 462  (of 3,000)
  exact-search baseline                          p50 1
```

Observations:

- **Recall is total, and the cost is selectivity.** 242 candidates against 1 for an exact search, so the verifier works far harder, while still reading 12x less than a full scan.
- **Ranking by closeness is free** during the verification pass you already run, since edit distance is computed on candidates you have already decoded.
- **The filter is document-level rather than term-level**, so a candidate may hold the chunks scattered across unrelated words rather than as the misspelled word itself. That is where the 242 comes from, and it is also why this cannot give you the document frequency of the matched variant without a second pass. A design that needs per-term statistics wants a Levenshtein automaton over a term dictionary instead.
- **Doing this on token bags directly does not work.** 39% of one-character typos share zero BPE tokens with the correct word, because a compression code desyncs when you change one symbol. Chunks are the right primitive precisely because damage stays local.

## What I would build

1. **The token bigram index.** This is the only item that changes the numbers. Whole words looked up in the unigram postings alone constrain 61 of 400 patterns, leave 98.4% of sub-word patterns with no constraint at all, and hand over 7.5% of the corpus on the word-aligned ones. Adding the bigram index takes coverage to 186 of 400 and selectivity to 0.8%.
2. **The 2 MB vocabulary sidecar**, static, built from the tokenizer at startup, which turns a sub-word literal into a candidate token set.
3. **Skip sparse grams.** They cost 2.7x the postings and 1.9x the build time for identical candidates.
4. **If you do not already run BM25 on token postings, build a dense trigram index instead.** It is smaller than what you would add, 2.93M postings against a 1.65M bigram index on top of a 0.77M unigram one, and it builds 5.7x faster. The token route wins on marginal cost and loses on absolute cost.

## Limitations

- **These are posting counts rather than bytes on disk.** A real encoder would compress the three differently, most likely favouring token postings since their lists are longer and their gaps smaller.
- **One corpus, one language.** Python from CodeSearchNet. CJK has [no word boundaries at all](/blog/token-search#the-real-payoff-one-analyzer-every-language), where the leading-space normalisation has nothing to hold onto.
- **Mined regexes are not search queries**, which biases the 53.5% fallback rate upward. I had no real code-search query log to check against, and that is the number I would most want before quoting a fallback rate to anyone.
- **My literal extractor is conservative.** It skips any group containing alternation and every lookaround, so it under-uses some patterns. That direction is safe, since dropping a constraint costs candidates and inventing one costs correctness.

```
python3 experiments/regex-filter/build_dataset.py      # corpus + mined patterns
python3 experiments/regex-filter/mine_agent_queries.py # agent greps from trajectories
python3 experiments/regex-filter/test_indexes.py       # sparse-gram soundness tests
python3 experiments/regex-filter/evaluate.py           # all methods, exact ground truth
python3 experiments/regex-filter/scale_run.py          # corpus-size sweep
python3 experiments/regex-filter/fuzzy_over_index.py   # typo search on the same index
```

`test_indexes.py` checks the two properties everything rests on: that my vectorised sparse-gram selection agrees with brute force on 400 random strings, and that a gram chosen from a query is always chosen inside a document holding it, which is the no-false-negatives guarantee.

## Key Takeaways

- **A token-bigram index turns BM25 postings into a regex filter that ties a dense trigram index candidate for candidate**, at 2.41M postings against sparse grams' 6.51M and 6.3 s of build time against 12.2 s. It computes the same function as a trigram index from storage that already exists for ranking.
- **The win is marginal cost, and it reverses if you have no token index.** Adding regex to existing BM25 postings costs a 1.65M-posting bigram index where a trigram index costs 2.93M from scratch, but the trigram index is smaller in absolute terms and builds 5.7x faster.
- **How many queries have no literal decides everything.** 53.5% for regexes mined from source, 3.7% for greps coding agents really run, and that one swap moves every index from 2.1x over a full scan to 11.4x. Quoting a speedup without a fallback rate says almost nothing.
- **Two predictions of mine died on contact with data.** A 5.2x sub-word win rested on dense trigrams returning 8x the true matches when they return 1.3x, and the advantage I expected to grow with corpus size shrank across a 16x sweep.
- **The tokenizer is a correctness decision.** WordPiece and SentencePiece fail to reassemble every one of 400 code files, so a regex derives chunks their index cannot hold. That rules them out before retrieval quality is discussed.
- **The recall check paid for itself four times**, including `"" in "?*"` evaluating to `True` and quietly truncating every literal. None of those bugs produced an obviously wrong number.
