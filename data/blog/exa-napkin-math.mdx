[Exa](https://exa.ai/) is a cool web search engine company. They [raised 85M\$ for Series B](https://exa.ai/blog/announcing-series-b) in September 2025. There are multiple parts of Exa AI architecture that they have described in their [blogs](https://exa.ai/blog). I've compiled them together and added some of my own notes and lots of assumptions for infra cost [napkin math](https://www.youtube.com/watch?v=IxkSlnrRFqc) as a fun exercise for myself. Please **take my estimates with a grain of salt** since it's not possible to be 100% right and my goal is to just get in the right ballpark. Also feel free to DM me on [X](http://kshivendu.dev/x) or [Linkedin](http://kshivendu.dev/linkedin) if you see any wrong or suboptimal assumptions :)

Update (October 2026): Exa has published more about its [index size](https://exa.ai/blog/what-is-web-indexing), [data pipeline](https://exa.ai/blog/exa-d), and [search pipeline](https://exa.ai/blog/composing-a-search-engine). I've rechecked the napkin math below against those details. The cost tables use assumed hardware prices and index coverage. So enjoy!

## 📦 Content Storage

Let’s estimate the storage requirements for large-scale text datasets:

- [Fineweb](https://huggingface.co/datasets/HuggingFaceFW/fineweb)
  - Its current default dataset has [25.9B rows and 53.4 TB of Parquet files](https://datasets-server.huggingface.co/size?dataset=HuggingFaceFW/fineweb), meaning 1B docs ≈ 2.06 TB of files. The earlier 44 TB figure was from the [original release](https://huggingfacefw-blogpost-fineweb-v1.static.hf.space/index.html). Mixing it with the current token count understated bytes per doc.
  - The [dataset card](https://huggingface.co/datasets/HuggingFaceFW/fineweb) reports over 18.5T GPT-2 tokens. Assuming 18.5T and the standard rule of 1 word = 1.3 tokens, 26B docs ~= 14.2T words.
    - 1 doc ~= 712 tokens ~= 547 words.
    - English words on [avg](https://www.wyliecomm.com/whats-the-best-length-of-a-word-online/) have 5 chars and 1 char = 1 byte, so 547 \* 5 bytes ~= 2.7KB / doc before spaces and punctuation
    - 1B docs ~= 2.7TB (estimated uncompressed)
- [English Wikipedia](https://en.wikipedia.org/wiki/Wikipedia:Statistics#Articles)
  - 7M docs occupy 24 GB (compressed), 1B docs ~= 3.42 TB (compressed)
  - It has 708 words / doc on avg. Assuming the standard rule of 1 word = 1.3 tokens, this means 920 tokens / doc on avg.
    - 1 doc ~= 920 tokens ~= 708 words
    - 708 \* 6 bytes ([reason](https://en.wikipedia.org/wiki/Wikipedia:Size_of_Wikipedia#Number_of_words)) = 4248 bytes
    - 1B docs => 4.2TB (estimated uncompressed)

Given these, let’s assume Exa’s crawlers curate pages and extract text efficiently enough such that:

- They are similar to [Fineweb](https://huggingface.co/datasets/HuggingFaceFW/fineweb) but a little more dense.
- 1B docs require 3TB (uncompressed) and 2.1TB (compressed)
- On avg **1 page ~= 600 words ~= 780 tokens ~= 3KB of letters before spaces and punctuation ~= 2.1KB compressed**. FineWeb's Parquet files give a rough size check. Exa's actual compression ratio is unknown.

| Resource          | Rate       | Volume for 1B docs | Cost/Month |
| ----------------- | ---------- | ------------------ | ---------- |
| **S3 storage**    | $0.02 / GB | 2.1 \* 1e3 GB      | $42        |
| **Ephemeral SSD** | $0.08 / GB allocated | 2.1 \* 1e3 GB | $168 |
| Total             |            |                    | $210       |

The SSD rate is my allocation assumption. On AWS, [instance-store SSD is included in the instance price](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/InstanceStorage.html). The $0.02 S3 rate is also rounded from the [published US tiers](https://aws.amazon.com/blogs/aws/aws-storage-update-s3-glacier-price-reductions/) of about $0.021-$0.023 / GB-month.

## 🔍 Lexical/Keyword search (BM25):

- They use the standard [BM25 algorithm](https://www.youtube.com/watch?v=ziiF1eFM3_4&t=698s) for lexical search
- Initially, this required about 1.8 TB RAM for 1B docs
- After optimizations in [this post](https://exa.ai/blog/bm25-optimization) it **dropped to 900GB (-50%)** RAM for 1B docs

### Napkin math

- Postings lists are a large part of the BM25 index, but Exa also found meaningful overhead in the data structures around them.
- As per [their blog](https://exa.ai/blog/bm25-optimization#:~:text=a%20single%20byte.-,Assuming%20the), each posting list entry takes:
  - doc_id → 4 bytes (uint32)
  - term_freq → 1 byte
  - 5 bytes total
- If the entire old index had consisted only of packed 5-byte entries, 1.8 TB / 5 bytes / 1B docs would mean 360 distinct indexed terms per doc. But Exa also counted tuple padding, allocations, and metadata in that 1.8 TB, so I can't derive the real term count from its total RAM.
- The vocab strings alone might be small: 10M terms \* 5 bytes / term = 50MB. Exa also pays for the lookup structures and short posting lists, so that 50MB isn't the whole vocabulary cost.
- Exa mentioned `uint32` doc IDs in the old representation. That doesn't tell us the global doc count since shards can use local IDs. Their [delta encoding](https://exa.ai/blog/bm25-optimization#:~:text=2.%20Variable%2Dlength%20%2B-,Delta%20Encoding,-for%20Document%20IDs) brought the average encoded ID down to 1.3 bytes in that design.
- I'm assuming that 100% of index is kept in RAM for faster iteration on posting lists (~2-5x faster compared to sequential reads in SSD - [source](https://github.com/sirupsen/napkin-math))

| Resource | Rate      | Volume | Cost/Month for 1B docs |
| -------- | --------- | ------ | ---------------------- |
| RAM      | $2 / GB   | 900GB  | $1800                  |
| SSD + S3 | $0.1 / GB | 900GB  | $90                    |
| Total    |           |        | $1890                  |

## 🧭 Vector search:

</div>

- As per [this](https://exa.ai/blog/building-web-scale-vector-db), they use [binary quantization](https://qdrant.tech/articles/binary-quantization) (BQ) and some clever CPU tricks for vector distance calculations ([SIMD](https://en.wikipedia.org/wiki/Single_instruction,_multiple_data) + precomputing possible outputs and keeping them in CPU registers for skipping calculation).
- They train [Matryoshka embeddings](https://huggingface.co/blog/matryoshka) with 4096 dims but only keep first 256 dims BQ vectors for index
- They use [IVF Index](https://youtu.be/chz74Mtd1AA?si=DvvDE3rO9HvVvox7&t=429) (also used in FAISS & pgvector) which an Approximate Nearest Neighbours Algorithm. It basically relies on k-means clustering, and during search time, finds the relevant clusters by comparing distance with respective cluster centroids, and only queries few of those clusters.
- They say they fetch extra results and re-rank them with uncompressed vectors. I assume a 1024d BQ stage and a 2048d f16 stage below to put numbers on the cost. Those stages are my guesses.

### Napkin math

- I use [Qwen3-Embedding-8B](https://huggingface.co/Qwen/Qwen3-Embedding-8B) as a cost and latency proxy since its dimensions fit the [description](https://exa.ai/blog/building-web-scale-vector-db#:~:text=4096%20floating%2Dpoint%20numbers). Exa says it [trained its own embedding model](https://exa.ai/blog/exa-api-2-0), so this doesn't identify their model.
  - Qwen3-Embedding-8B has a 32K-token context length. A long context does not show that Exa embeds every full page as one vector. I assume one page = one vector for this calculation.
- Let's estimate the storage requirements of vectors
  - Each original vector would take 4096 dims \* 2 bytes (assuming fp16) = 8192 bytes. This means 1B vectors would take 8.192 TB for 1B docs.
  - By truncating matryoshka to 256 dims it becomes 512 GB for 1B vectors.
  - With binary quantization, 16 bits (since fp16) becomes 1 bit. So 512 GB / 16 = 32 GB per 1B vectors or **32 bytes (256 bits) per vector**
  - Note how MRL truncation + BQ led to 16\*16=256x reduction
- For IVF index with MRL truncated 256d BQ vectors for their "neural search"
  - IVF Index needs centroids generated from k-means clustering algos. Exa reported [100k clusters](https://exa.ai/blog/building-web-scale-vector-db) for its older system. For this 20B-vector calculation, let's assume **200k clusters, each having 100k vectors**. That newer cluster count is my guess.
  - Each cluster will have a centroid and I'm assuming they compare with uncompressed centroid vectors for maximizing recall.
  - Centroids will require 200k \* 4096 \* 2 bytes (f16) ~= 1.64 GB
  - Each vector ID needs to be stored in the IVF Index. Assuming 8-byte IDs, 20B \* 8 bytes = 160 GB. Local shard IDs could be smaller.
  - Each 256d truncated + BQ compressed vector will take 32bytes (256 bits), so 20B \* 32 bytes = 640 GB
  - So total requirements are like 1.64 + 160 + 640 GB ~= 802 GB for 20B vectors
    - This is 40GB for 1B vectors
    - Index size is just 40/8000\*100 = 0.5% of the full vectors (nice!)
- For 1st stage re-ranking with 1024 dim MRL truncated BQ vectors:
  - Storage for 1B vectors takes 128GB (1024 / 8 \* 1B / 1e9)
- For 2nd stage re-ranking with 2048 f16 vectors:
  - Storage for 1B docs takes 4096GB (8.192TB/2). This is okay for disk but storing all of them in RAM would be too costly.
  - Let's assume 25% (1024 GB) is cached in RAM.
- In this cost scenario I keep the index and 1024d BQ vectors in RAM, plus a quarter of the 2048d vectors. I also count local disk and S3 copies. [Exa-d](https://exa.ai/blog/exa-d) uses S3 for its data pipeline. The serving copies here remain my assumption.

| Component                        | Rate      | Volume | Cost/Month for 1B docs |
| -------------------------------- | --------- | ------ | ---------------------- |
| Index RAM                        | $2 / GB   | 40GB   | $80                    |
| Index Ephemeral SSD + S3         | $0.1 / GB | 40GB   | $4                     |
| 1024d BQ Vectors in RAM          | $2 / GB   | 128GB  | $256                   |
| 1024d BQ Vectors in SSD + S3     | $0.1 / GB | 128GB  | $12.8                  |
| 2048d Vectors RAM                | $2 / GB   | 1024GB | $2048                  |
| 2048d Vectors Ephemeral SSD + S3 | $0.1 / GB | 4096GB | $409.6                 |
| Total                            |           |        | $2810.4                |

Note how this is 2.8k / 1.9k = **~1.5x of lexical search** and **73% of it comes from the assumed 2048d vectors in RAM for re-ranking**. Including their disk copy, those vectors account for 87%.

## 🗂️ Metadata storage:

- For each web page, they also need to store metadata like title, url, publishedDate, author, id, image, favicon, text, summary, etc.
- Their [search API example](https://docs.exa.ai/reference/search) returns page attributes such as title, URL, and dates. Let's assume 512 bytes per page for metadata, with full text and summaries counted separately.
- So total metadata storage on disk + S3 is 1B docs \* 512 bytes = 512GB for 1B doc metadata
- Assuming that metadata for the same 25% points are cached, we need 128GB of RAM

| Component                   | Rate      | Volume | Cost/Month for 1B docs |

| Metadata RAM                | $2 / GB   | 128GB  | $256                   |
| Metadata Ephemeral SSD + S3 | $0.1 / GB | 512GB  | $51.2                  |

## 🌐📤 Network egress costs:

The APIs respond back to the user and that also costs money. [Napkin math](https://github.com/sirupsen/napkin-math) says it's `$0.1` per GB for "internet egress"

I did a basic search API call with Exa and response size was around 3KB. In [October 2026, Exa said](https://www.linkedin.com/company/exa-ai/) it handles 2B requests per month. Over a 30-day month, that's about **772 external requests per second on average**. Peaks and the number of internal retrieval calls per request are unknown. Also, Exa hasn't said what share of those requests are plain web searches versus Contents, Agent, or other products.

If all 2B responses were as small as my 3KB sample, 3 KB \* 2B = 6,000 GB of egress, or **$600/month** at the assumed $0.10/GB. That is a small-response scenario, since full page contents and agent outputs can be much larger.

## 🔢 Embedding generation:

- As we [previously](#-content-storage) derived/assumed, let's say each Exa doc has 780 tokens.
- If they were to embed 1B docs with OpenAI `text-embedding-3-large` embedding in batches (see [pricing](https://platform.openai.com/docs/pricing#embeddings))
  - 780 \* 1B \* 0.065 \$ / M token = 50.7k \$ for 1B docs (insane!)
  - Exa uses its own model, so this gives us a public API comparison.
- As per [this benchmark](https://www.tensoreconomics.com/p/why-are-embeddings-so-cheap#:~:text=a%20million%20tokens.-,In%20Tab.%202), Qwen3-Embedding-8B on an H100 processed 33,488 tokens/s with 1040-token inputs and batch size 4. At 100% utilization and \$2 / GPU-hour, that's $0.0166 / 1M tokens. My 780-token pages and Exa's own H200 model may run differently.
  - 780 \* 1000 \* 0.0166 \$ / M token ~= 13k $ for 1B docs.
  - This is much better! However, notice that this still surpasses all the costs.
  - Exa bought/built their [Exacluster](https://exa.ai/blog/meet-the-exacluster) for embedding and training workloads:
    - [Vast's GPU prices](https://vast.ai/pricing) vary by machine and reservation type. The $2 / H100-hour above comes from the Qwen benchmark.
    - Exa says the cluster cost [5M\$](https://exa.ai/blog/meet-the-exacluster) for 144 H200s and draws about 100kW. Spreading $5M over three years of 24/7 use gives about $1.32 / GPU-hour. At an assumed $0.10 / kWh, power adds about $0.07 / GPU-hour. That's $1.39 before hosting, repairs, and idle time.
    - I'll still use 1.5\$ / effective GPU-hour as an optimistic scenario. The same Qwen benchmark becomes 0.0166 / 2 \* 1.5 ~= 0.0125 \$ / 1M tokens. Exa's own model and GPU throughput may differ.
    - Exacluster has H200s & A100 instead of H100s. But let's assume the same rates.
    - Note that the Exacluster is also used for training embedding model and re-ranker so there's more value to be derived from the Exacluster.

| Embedding model               | Rate             | Tokens    | Cost for 1B docs |
| ----------------------------- | ---------------- | --------- | ---------------- |
| OpenAI `text-embedding-3-large` Batch | $0.0650 / 1M tok | 780 \* 1B | $50.7k |
| Qwen on Rented H100 GPUs      | $0.0166 / 1M tok | 780 \* 1B | $13k             |
| Qwen on Exacluster            | $0.0125 / 1M tok | 780 \* 1B | $9.75k           |

In this scenario the difference is **3.25k$ / 1B docs** per embedding pass. For 20B docs that's **65k USD per full pass**, or **234k USD / year** if 30% of the whole index is re-embedded every month. I can't claim that as Exa's actual saving without knowing the full cost and utilization of their cluster.

## Re-ranker:

- I use a [Qwen Reranker](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B#qwen3-embedding-series-model-list) as another cost proxy. Exa says it trained its [own reranking models](https://exa.ai/blog/evals-at-exa).
- Public [providers](https://deepinfra.com/Qwen/Qwen3-Reranker-0.6B) charge \$ 0.010 \/ 1M tokens for the 0.6B model. Let's assume the same rates.
- It compares 1 query (same 10 tokens) against 100 documents (each with 780 tokens avg). Total tokens: 100 \* (780 + 10) = 79k
- Note: This is purely a **search time cost** unlike document embeddings which have to be stored/maintained beforehand.

| Re-ranker model       | Rate             | Tokens / query | Cost of 1k queries |
| --------------------- | ---------------- | -------------- | ------------------ |
| `Qwen3-Reranker-0.6B` | $0.0100 / 1M tok | 79k            | 0.790 \$           |
| `Qwen3-Reranker-4B`   | $0.0250 / 1M tok | 79k            | 1.975 \$           |
| `Qwen3-Reranker-8B`   | $0.0500 / 1M tok | 79k            | 3.950 \$           |

If all 2B monthly requests were searches that re-ranked 100 full documents, the 0.6B proxy above would cost **$1.58M/month** at this public API price. If only 10% took that path, it would be **$158k/month**. Scoring 100 passages of 100 tokens instead of full documents on every request would be **$220k/month**. These are workload examples, since Exa hasn't disclosed the search share, candidate lengths, or cost of its own reranker. The old overall table didn't include any re-ranker cost.

## 🕷️ Crawling updates

- This [research paper](https://snap.stanford.edu/class/cs224w-readings/Fetterfly03PageEvolution.pdf) found that web page changes vary a lot by page and domain, and many changes are trivial or just markup. It doesn't establish a 25% monthly re-embedding rate for Exa.
- There might be a single digit **monthly growth of the dataset - say 2%** (assuming aggressive crawling)
- Content disappearance: ~0.5% monthly
- Overall let's assume **30% monthly re-embedding** for changed and new content. [Exa-d](https://exa.ai/blog/exa-d) can update specific derived fields and can also rebuild embeddings for the whole index when Exa changes models. Exa's actual refresh fraction could differ.

## 💰📊 Overall costs:

I used 20B docs for the [Exa 2.0 launch](https://exa.ai/blog/exa-api-2-0), when they said they crawled and parsed tens of billions of pages. In [August 2026](https://exa.ai/blog/exa-firefox), Exa said it served an index of **100B documents** and tracked **1.4T URLs**. Those are different counts. Let's run both page counts through the same assumptions. I don't know whether all 100B pages have every vector and BM25 structure in my table.

The 30% refresh assumption only multiplies **new embeddings each month**. RAM and storage are charged on the full index every month. I use Exa's newly disclosed 2B monthly requests for both scenarios. The egress and re-ranking calculations treat those requests as searches to show the cost at that traffic level. The actual product mix could change both costs.

The first full embedding pass is **$195k for 20B docs** or **$975k for 100B docs** under the assumed $9.75k / 1B rate. It's a one-time compute job. The storage rows above recur every month, even when the pages don't change.

The 100B refresh scenario also needs a capacity check. At 30%, that's 30B pages or 23.4T tokens embedded every month. At the [Qwen H100 benchmark's](https://www.tensoreconomics.com/p/why-are-embeddings-so-cheap) 33,488 tokens/s, 144 GPUs running flat out would take about **56 days**. The [144 H200 cluster](https://exa.ai/blog/meet-the-exacluster) was Exa's 2025 disclosure. Its [current about page](https://exa.ai/about) says it has hundreds of H200s, without giving an exact count. Exa's own model and H200 throughput could also differ. The old 144-GPU fleet gives a check on my throughput assumption. Exa has more capacity now.

And the query re-ranker can be a big extra line. Using the public-price proxy above, the 2B-request scenario runs from **$321k/month** if 10% of requests re-rank 100 full docs to **$1.74M/month** if every request does. At 100B indexed pages, the same examples are **$973k to $2.39M/month**. The passage-length example lands at **$383k/month** for 20B pages and **$1.03M/month** for 100B pages. These examples don't reveal Exa's actual bill: requests span products, and Exa uses its own models.

The new traffic number also gives a rough check on revenue. Exa [said it passed $100M in annualized revenue](https://www.linkedin.com/company/exa-ai/). At 2B requests/month, that's more than **$8.33M/month** of revenue run rate, or more than **$4.17 per 1,000 requests** if spread evenly across them. Charging every request the [entry $4/1k Instant price](https://exa.ai/pricing) gives $8M/month, or $96M annualized. That's close, but Exa also sells Fast, Deep, Contents, and Agent work at different prices, and large customers have custom contracts. At the $100M threshold, my $815k 100B-page subtotal is about 9.8% of the monthly revenue run rate. The every-request, full-document reranker example would bring it to about 28.7%. Neither percentage is a margin estimate: the model still leaves out major costs, and the disclosed totals don't tell us the revenue or cost of a typical web search.

Exa has also described a [separate entity-search path](https://zilliz.com.cn/blog/exa-zilliz-cloud-agent-search) for people, companies, and other structured objects. It says its own ML pipeline enriches entities and creates dense and sparse vectors. The search layer combines semantic and keyword matches with reciprocal-rank fusion, then adds structured metadata for API results. Exa says its main web index stays on its internal infrastructure. The web-page cost table leaves out the entity collections and their managed serving. Reciprocal-rank fusion combines result lists. The model re-ranker priced above scores candidate text.

Other dedicated data is now public: Exa reports an index of about [350M publications and 30M authors](https://exa.ai/blog/publications-search), plus [211M places with structured fields](https://exa.ai/blog/places-search). I don't add those counts to the 100B web pages because they are different kinds of records and may overlap with the web index. The [Dynamic Highlights](https://exa.ai/blog/dynamic-highlights) feature also runs a model over retrieved content. Exa reports 95% fewer output tokens than full pages in its evaluation, but that inference and the varying response sizes are absent from my 3KB egress example.

I still haven't priced crawling, clustering, replicas, query CPU/GPU, model training, extra artifacts in [exa-d](https://exa.ai/blog/exa-d), or LLM calls in products like Deep. Exa also now says it has [over 400B webpage snapshots](https://exa.ai/blog/exa-snapshot), which my one-current-copy content row misses. The $2/GB RAM and SSD allocations also need checking against the real machines. So I wouldn't call either subtotal a minimum or extrapolate it to another company's URL count.

## ⏱️ Search latency analysis:

### Network latency:

I queried Exa AI DNS records and looks like they are only present in AWS `us-west-2` region. This has downsides because it increases latency a lot. The round trip time from India is `600-800ms`. You can find ping times from all over the world [here](https://globalping.io/?measurement=g9UVVPjZD7g3OmqV). There are two solutions to this:

- Expand into new regions. But it's very costly to replicate whole infra in different region.
- Use something like Cloudflare Edge network. It basically proxies the requests through Cloudflare edge network which is faster and more stable than traditional internet route. It's not zero overhead, but is definitely a big improvement.

Update: Looks like Exa has switched to Cloudflare Edge like Perplexity with Exa 2.0. This means the latency across the globe has decreased. I see that now the round trip latency for empty request from India is at `300-400ms`. Good job, Exa team!

You can also use these commands to get rough idea of latency:

```sh
time curl --head https://api.exa.ai/search # from your machine
globalping http api.exa.ai from World --host api.exa.ai --path '/search' --limit 20 --latency # globally
```

### Lexical search latency

The [Exa blog](https://exa.ai/blog/bm25-optimization) says they get sub-500ms latency for retrieving thousands of top results with lexical search. It doesn't label that number p50. Exa's [newer pipeline description](https://exa.ai/blog/composing-a-search-engine) shows dense and sparse retrieval running in parallel in one example, so I can't infer that Fast uses only neural search from the BM25 latency alone.

BM25 can have more latency variation than vector search in some setups, especially with:

- Longer queries (More posting lists to scan. This downside can be saturated using [wAND](https://izihawa.github.io/summa/blog/how-search-engines-work) but you still see more variance in latency)
- More data (less pronounced. But this happens especially if you get common but non-stopword terms)

For example, [this Vespa benchmark](https://blog.vespa.ai/pretrained-transformer-language-models-for-search-part-4/#:~:text=Benchmarking%20Results) used 9M MS Marco passages and measured end-to-end latency under roughly 70% CPU load:

| Retriever      | Average latency (ms) | p999 latency (ms) |
| -------------- | -------------------- | ----------------- |
| Lexical (WAND) | 16.83                | 209.40            |
| Dense (ANN)    | 18.58                | 28.70             |

You can see how avg latency is similar for both vector search and lexical search but p999 is **7.3x** more for lexical search in this benchmark. Exa uses a different index, corpus and hardware, so this ratio can't predict its tail latency.

At tens of billions of docs, I would expect posting list shards queried in parallel and then merged, but Exa hasn't published that shard layout.

### Neural search latency (Exa fast)

[Previously](https://exa.ai/blog/fastest-search-api) Exa Fast search had p50 = 423ms and p95 = 604ms in the published chart, measured from us-west-1.

[With Exa 2.0](https://exa.ai/blog/exa-api-2-0), the chart shows p50 = 346ms and **p90 = 462ms**, measured from us-west-2. So the two p50 values differ by 77ms, though the benchmark setups also changed. We can't subtract 462 from the old p95 of 604ms: p90 and p95 measure different parts of the latency distribution.

What happened inside that 423ms? This diagram is my sketch of possible components, not a measured Exa trace:

![Exa Search Pipeline](/static/images/blogs/exa-search-pipeline.svg)

- Network latency: They measured roughly 50ms from their benchmark region.
- Query embedding generation with as per [this](https://www.tensoreconomics.com/p/why-are-embeddings-so-cheap#:~:text=despite%20batch%20size%20increasing) on H100 SXM:
  - 1040 tokens with batch size = 1 => 25RPS => 40ms
  - 520 tokens with batch size = 1 => 34RPS => 29ms
  - 260 tokens with batch size = 1 => 37RPS => 27ms
  - 260 tokens with batch size = 8 => 63RPS => 15ms
  - 260 tokens with batch size = 16 => 77RPS => 12ms
  - The benchmark uses Qwen3-Embedding-8B on an H100, with at least 260 input tokens. A 10-token Exa query on Exa's own model doesn't have a measured time here.
- Vector retrieval, fetching content, and re-ranking also take time. Exa now says independent search nodes can run [concurrently](https://exa.ai/blog/composing-a-search-engine), so subtracting guessed sequential stages from the 423ms p50 would give a false breakdown.
- Exa 2.0 mentioned new clustering, lexical compression, and assembly optimizations. I can't split the p50 change between those and model or reranker changes from the public numbers, especially with two different benchmark setups.
- In [February 2026](https://exa.ai/blog/exa-instant), Exa launched Instant at sub-200ms. That's a different endpoint, so I wouldn't compare it as a direct Fast regression or improvement.

## What if Exa used HNSW instead of IVF?

- In [this billion-scale KNN benchmark](https://blog.vespa.ai/billion-scale-knn-part-two/), a 72 vCPU machine handles 1B binary vectors:

  - Search latency of HNSW: 2ms with recall 50% and 4ms with 90% recall with k=10
  - HNSW indexing lowers write throughput and raises memory use compared with the no-HNSW setup. The article's indexing graph shows the tradeoff, but it doesn't give a per-write latency from dividing CPU count by throughput.

- I previously projected 100-200ms IVF search and around 5ms HNSW search at 10B docs from `sqrt(N)` and `log(N)` ratios. That was too much to infer from those asymptotic expressions. The real comparison needs the same vectors, recall target, filters, hardware, shard layout and update load. Exa's clustering design trades extra candidate scanning for a smaller index that's easier to shard and filter.
- Similar flaws of scaling IVF were also demonstrated in [my previous benchmark blog with Nirant](https://nirantk.com/writing/pgvector-vs-qdrant) that compared Qdrant's HNSW and PGVector's IVF Index and our blog accelerated the implementation of HNSW in pgvector.
- If Exa switched to HNSW, it would likely pay more for graph memory and indexing CPU. Whether recall or latency improved would need a like-for-like benchmark. Exa kept improving its clustered index at [tens of billions of pages](https://exa.ai/blog/exa-api-2-0), so HNSW isn't an obvious free win here.

## Key takeaways:

- Exa applies heavy compression through matryoshka embeddings and binary quantization, then offsets the loss with uncompressed vectors and re-ranking.
- The public docs show a query pipeline with dense and sparse retrieval, fusion and re-ranking. At 2B monthly requests, scoring 100 full documents on every request would dominate this napkin cost model. Exa hasn't disclosed how often that happens.
- Documents on the web change over time and cost of re-indexing (document embedding generation + k-means clustering) is high. To mitigate this, Exa built their ExaCluster.
- Exa now says it serves a 100B-page index. Under my assumptions, the recurring storage, refresh, and small-response egress subtotal is $815k/month at that size. The real bill depends heavily on how many pages get each index structure and what share of requests use each product.

## Closing remarks:

Web search started in 1994 with [Yahoo directories](https://en.wikipedia.org/wiki/Yahoo_Directory), then search engines like Alta Vista introduced Keyword search using [TF-IDF](https://en.wikipedia.org/wiki/Tf%E2%80%93idf) in late 1990s, and then eventually Google came in 1998 and dominated the game with [Pagerank](https://en.wikipedia.org/wiki/PageRank). Over the next two decades, Google added lots of heuristics and statistics based approaches. Then around 2015 they started integrating ML models such as RankBrain and BERT, enabling semantic understanding and context-aware ranking.

And very recently, we see that even those are being [surpassed](https://exa.ai/blog/evals-at-exa) by more generalizable LLMs. Infact, now you can ask more [complex queries](https://exa.ai/blog/websets-evals) to the web which were impossible with previous techniques. It's literally [Bitter lesson](http://www.incompleteideas.net/IncIdeas/BitterLesson.html) 101 which says approaches that scale with compute beat human designed heuristics.

We’re entering an era where startups are on their way to recreate Google scale search and number of searches will rise exponentially because of AI agents driving majority of search request. That's why products like Exa, Parallel, and Perplexity are effectively "caching" the web and serving "reads" in an optimized way. While others like Perplexity Comet, OpenAI Operator, etc want to "write" to the web (i.e. take actions). **Web and search are changing fast** and I'm very excited about their futures!
