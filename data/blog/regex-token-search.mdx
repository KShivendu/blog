> Looking for TL;DR? Check [key takeaways](#key-takeaways)

In [Token Search](/blog/token-search) I ran BM25 on the model's own BPE token IDs and it matched a Porter-stemmed English analyzer. That post was about ranking. This one asks whether the same postings can answer a different question: which documents match `/colou?r of the (sky|sea)/`, and can they do it faster than a scan.

[TopK's sparse-gram post](https://www.topk.io/blog/20260814-fast-regex-search-sparse-grams) is the state of the art here. They hash character bigrams with CRC32, select a gram when its two boundary bigrams outweigh every bigram in its interior, compile the regex into a boolean expression over those grams, and verify survivors with the real regex. The selection rule is content-defined, so a gram picked from a query string is guaranteed to be picked from any document containing it.

Short version of what I found: token postings do the same job in **a quarter of the storage**, tie on the common case, and should win on sub-word literals once you add a bigram index. The same idea fails on fuzzy search, and the failure is measurable rather than a matter of taste.

**Read this next to [the benchmark](/blog/token-search-regex).** I built the experiment this post asks for. The storage argument held, 3.25x measured against 3.9x modelled. The sub-word latency argument did not: it rests on dense trigrams returning 8x the true matches, and measured they return 1.3x. Every latency figure below is a model, and the one marked 5.2x is now known to be wrong. I have left them in place so the reasoning and its failure are both readable.

This post is a design dump, not a finished result. Every number below comes from a script in `experiments/regex-filter/`, and I say which one.

## The invariant that decides everything

A prefilter has one obligation. It may hand the verifier junk, but it must never drop a document that actually matches. Extra candidates cost time, a missing candidate is a wrong answer.

TopK's CRC32 rule buys that obligation because selection depends only on the bigrams inside the gram span. Whether `archi` is indexed depends on `ar rc ch hi` and nothing else, so query and document agree without communicating. Grams touching the query's edges depend on characters outside it, so those get dropped, which is their `covering(q) ⊆ all(q) ⊆ all(d)`.

BPE does not have that property. Merges apply in global rank order across the whole pretoken, so a suffix rewrites the prefix:

```
  "in"            ->  [in]
  "ing"           ->  [ing]           the [in] is gone
  "token"         ->  [token]
  "tokenization"  ->  [token][ization]
  "kenizat"       ->  [k][en][izat]   shares nothing with either
```

So a substring of a word does not tokenize to a substring of that word's tokens.

The fix is already in Token Search. `enc.encode(" " + word)` makes each word tokenize independently of its surroundings, which is the same `covering()` trick at a coarser unit. The invariant holds at **word** granularity: take the whole words strictly inside a regex literal, drop partial words at the edges.

```
  regex:  colou?r of the (sky|sea)

  TopK:   " the" AND "r of t" AND ("e se" OR "e sk")
  token:  [of] AND [the] AND ([sky] OR [sea])
          AND ([col][our] OR [color])
```

TopK's own example is entirely word-aligned, which is typical. Most real regexes hang off literal words.

## What the existing index already gives you

Token Search's posting lists are the filter index. No second structure, no extra write path. A multi-token literal like `tokenization` becomes an ordered phrase, and an AND over `[token]` and `[ization]` is a superset of the real matches, which is all a filter owes you.

Selectivity is the open question, and [Token Search already measured it](/blog/token-search#three-views-of-the-posting-list-blow-up). Searching `veal` in a 2,953-document corpus:

```
  posting entries read for the query "veal"

  word index      ##                                     2
  token IDs       ############                         305
  char trigram    ####################################  5,192
  char bigram     ##################################### 13,799
```

Observations:

- **Token IDs sit 17x better than char trigrams and 150x worse than exact words.** That gap is the entire reason TopK needed sparse grams in the first place, and Token Search measured it before I started.
- **The gap closes with word-tuple keying.** Fix 1 in Token Search keys a term by the whole word's token-ID tuple, so `belvidere` stops paying three independent subword IDFs. For filtering it collapses `veal` back to a df-2 list. I built it for ranking, it doubles as the high-selectivity filter key.

## The second index, and what it costs

Two structures, and "n-grams on the token vocab" means either one depending on how you read it.

```
  (a) n-grams OF token IDs              (b) char n-grams OVER the vocab
      corpus-level, grows with data         static, 200k tokens, never changes

      [the][ cat] -> one term               "Tokenizer" -> tok, oke, ken, ...
      [ cat][ sat] -> one term              index: trigram -> {token ids}
```

Measured on 631 pseudo-documents chunked out of this repo (`arm_plan.py`):

| index         |   terms | postings | mean df |
| ------------- | ------: | -------: | ------: |
| token unigram |  17,431 |  145,015 |     8.3 |
| token bigram  | 115,243 |  230,750 |     2.0 |

And the vocab sidecar over all of `o200k_base` (`vocab_index.py`):

```
  whole vocab text            1.10 M chars, 198,438 utf-8-decodable tokens
  3-gram index               63,245 distinct, 708,808 postings, ~2 MB
  tokens per trigram         p50=2  p90=14  p99=204  max=4730
```

Observations:

- **The bigram index costs 1.59x the unigram postings** and drops mean document frequency from 8.3 to 2.0, so it is doing real work as a selectivity source, not just bookkeeping.
- **The vocab sidecar is 2 MB and static.** It is built once from the tokenizer, never rebuilt on ingest, and shared across every field and collection, because the vocabulary is fixed at 200k before any data arrives.
- **Its fan-out is tiny for the literals that matter.** `keniz` is contained in exactly 3 tokens (`Tokenizer`, ` tokenizer`, ` tokenize`), `quantum` in 1, `belvid` and `xylo` and `gRPC` in none. The common ones blow up (`ing` in 3,583 tokens, `the` in 395), but you would never use those as the selective constraint.

## Sub-word literals, and the straddle problem

The vocab index answers "which token IDs could contain this literal," which is the thing plain token postings cannot do. `/keniz/` finds 3 tokens outright. But it can also sit across a boundary:

```
  t o k e n i z a t i o n
  [token   ][ization    ]
       ^^^^ ^^
       ken   iz          -> no single token has it
```

How often does that happen? I measured it three ways, and I got one of them wrong the first time.

```
  28.0%  of a word's trigrams sit in no single vocab token
  77.6%  of words have >=1 trigram straddling their own token boundary
   2.9%  of words have >=1 trigram that no vocab token contains at all
```

Note the correction. I first reported 97.4% for the second line, computed by padding each word with two spaces on both sides. That pad manufactures trigrams like `" t"` that no token could ever hold, so it inflated the number. The honest figure is **77.6%**, and the separate 2.9% line is the subset where the straddle path is not merely useful but mandatory. The conclusion survives, the number did not.

So the straddle path is the common case, not an edge case, and a filter built only on single-token containment is incomplete for three words in four.

## The arm explosion, and the trap I fell into

A literal can align against tokens in many ways. Enumerating them from the vocabulary alone over-generates badly (`arm_plan.py`, step 1):

| literal   | enumerated (A,B) pairs |
| --------- | ---------------------: |
| `ization` |                    778 |
| `gRPC`    |                  5,636 |
| `keniz`   |                 19,425 |
| `_id`     |                 18,055 |
| `veal`    |                213,970 |
| `earch`   |                236,907 |

`veal` is 213,970 because 726 tokens end in `ve` and 292 start with `al`.

The obvious relaxation is to keep only the cheapest conjunct per arm, since a superset is legal. It is a trap, and I ran it before I saw why:

```
  'keniz' ->  7,301 lists  ->  113 lists   looks like a 65x win
              but it picks:  =en  =i  =n  =ni
  'utf-8' ->    118 lists  ->    1 list
              it picks:      =-
```

Observations:

- **List count collapsed and posting volume exploded.** Every conjunct it chose is a single-character token sitting in essentially every document, so `utf-8` reduces to "documents containing a hyphen."
- **The lesson is that plan cost is document frequency, not list count.** Optimising on the wrong one picks exactly the worst lists.

## The bigram index prunes the explosion, soundly

Most enumerated splits never happen, because BPE is deterministic. Checking the enumerated pairs against pairs that actually occur adjacently (`arm_plan.py`, step 3):

| literal   | enumerated | real |  pruning |
| --------- | ---------: | ---: | -------: |
| `ization` |        778 |    1 |     778x |
| `quantum` |        902 |    1 |     902x |
| `gRPC`    |      5,636 |    2 |   2,818x |
| `_id`     |     18,055 |    2 |   9,028x |
| `keniz`   |     19,425 |   29 |     670x |
| `veal`    |    213,970 |    1 | 213,970x |
| `earch`   |    236,907 |    1 | 236,907x |

And on real text each literal only ever lands on one or two alignments (`arm_plan.py`, step 4):

```
  'keniz'    257 occurrences, 2 alignments:  ken|iz x144   keniz x113
  'ization'  239 occurrences, 2 alignments:  ization x238  iz|ation x1
  'earch'    939 occurrences, 2 alignments:  earch x932    e|arch x7
  'veal'      13 occurrences, 2 alignments:  veal x11      ve|al x2
  'belvid'     7 occurrences, 1 alignment:   bel|vid x7
```

Observations:

- **The prune is sound, not heuristic.** The bigram index is built from the same corpus, so a pair that never occurs adjacently there cannot appear in any document of that corpus. Nothing is dropped.
- **The gap between 19,425 and 29 is the whole argument for index (a).** The vocab index generates candidates and the bigram index says which ones are possible in fact.

The combined pipeline:

```
  /tokeniza[a-z]+/
        |  regex -> required literals
  "keniz"
        |  (b) vocab 3-gram index, 2 MB static
  arms: 3 single tokens  OR  (ends "ken") x (starts "iz") = 19,425 pairs
        |  (a) corpus token-bigram index
  arms: 3 single tokens  OR  29 real adjacent pairs
        |  intersect corpus posting lists
  candidates
        |  decode + verify, or a token-alphabet DFA
  matches
```

## Napkin math: storage and latency

Constants from [Simon Eskildsen's napkin-math](https://github.com/sirupsen/napkin-math), one core, and the full model is `napkin.py`.

```
  corpus        10M docs x 2 KB      = 20 GB UTF-8
  tokenized     4 B/token, o200k     = 500 tok/doc, 5.0 G tokens

  posting decode         250 M postings/s
  random NVMe @ depth      1 GB/s        sequential  3 GB/s
  RE2 + literal prefilter  1 GB/s        no prefilter  100 MB/s
  BPE detokenize           2 GB/s
```

| index                  | postings |  size | vs corpus |
| ---------------------- | -------: | ----: | --------: |
| TopK sparse byte grams |   30.0 G | 75 GB |     3.75x |
| token unigram          |    3.5 G |  5 GB |     0.26x |
| token bigram           |    5.6 G | 14 GB |     0.70x |
| vocab 3-gram sidecar   | 0.0007 G |  2 MB |        ~0 |

Observations:

- **TopK's sparse index is bigger than a dense trigram index, not smaller.** Their `E[grams] ~= 2L` has `L` in bytes, and at the minimum length 3 the selection probability is exactly 1, so every trigram is indexed (that is `L`) and the longer sparse grams add roughly `L` again. Sparsity is measured against dense-all-lengths (`L x N`), so what it buys is selectivity, not size.
- **Token postings win 3.9x on storage** (75 GB against 19 GB) for one reason: a posting covers 4 bytes instead of half a byte. That comes straight from token-native storage, not from anything clever in the filter.

Latency, against a 27 s full-scan baseline:

| query                                          |      TopK |     token |         ratio |
| ---------------------------------------------- | --------: | --------: | ------------: |
| word-aligned `/colou?r of the (sky\|sea)/`     |     89 ms |    104 ms |         0.85x |
| rare literal `/belvidere/`                     |   `<1 ms` |   `<1 ms` |           tie |
| sub-word `/keniz/` (modelled, since disproven) |    162 ms |     31 ms | ~~5.2x~~ 1.0x |
| wildcard `/[a-z]{3}[0-9]+/`                    | 20 s scan | 12 s scan |   1.7x on I/O |

Observations:

- **Word-aligned queries are a tie, and token is nominally behind.** Traversal is 4.2 ms of a 104 ms query. Fetch and verify dominate and both methods pay them identically, because they land on the same candidate set. The extra 20 ms is detokenizing before the regex runs.
- **The sub-word win comes from adjacency, not from tokens.** `ken`, `eni`, `niz` all appearing somewhere in a document does not put them next to each other, so trigrams admit "kennel ... genie ... organize". The bigram index requires them contiguous.
- **TopK's adjacency claim is weaker than it reads.** They select an n-character gram with probability `2/((n-1)(n-2))`, so a 5-character literal gets its adjacency-carrying gram **1 time in 6**. The other five times the query runs on trigrams, which carry no adjacency at all.
- **On the fallback path token still wins on I/O**, scanning 12 GB of token payload instead of 20 GB of UTF-8, because the payload is the compressed form.

The candidate counts in that table are assumed, not measured, and they drive everything. The 8x false-positive rate for trigrams on `/keniz/` is the load-bearing guess. If it is really 2x, row three collapses to a tie and the whole comparison becomes "4x smaller index, same speed."

## Verification runs on tokens

The payload is token IDs, so step 3 either decodes first or runs the regex DFA over the token alphabet by memoising `(dfa_state, token_id) -> next_state`:

```
  byte DFA:    s -> e -> a -> r -> c -> h      6 steps
  token DFA:   [search]                        1 step, after warmup
```

The table is bounded by 200k x the DFA's state count, small for short patterns, and it removes the 20 ms decode from the latency table above. This is the piece I would actually build.

## Fuzzy search: same architecture, opposite answer

The architecture transfers. The representation does not, and the failure is large.

I generated one edit-distance-1 typo for each of 8,000 English dictionary words and measured overlap with the original (`fuzzy_robustness.py`):

| representation   | Jaccard |   p50 | shares >=1 term |
| ---------------- | ------: | ----: | --------------: |
| BPE token bag    |   0.191 | 0.200 |           61.0% |
| char trigram bag |   0.499 | 0.500 |          100.0% |

Observations:

- **39% of single-character typos share zero BPE tokens with the correct word.** A bag-of-tokens fuzzy filter drops two typos in five. Char trigrams never hit zero on words of that length.
- **The reason is that BPE is a compression code.** Compression codes desync when you change one symbol. Trigrams are a sliding window, so damage stays local. Opposite design goals, and the examples make it concrete: `person` is `[1647]` and `eprson` is `[319, 638, 1356]`, `arrogant` is `[112497]` and `rrogant` is `[428, 12885, 493]`.
- **Typos make BPE fragment 41% harder**, 2.04 tokens per clean word against 2.87 per typo. That is useless as a retrieval signal and useful as a misspelling detector, which solves the real practical problem of deciding when to fuzzy-expand at all.

I also tested the direct version of "reuse the vocab n-grams for fuzzy": expand each token of the typo to its trigram-neighbour tokens, then OR the posting lists. It recalls the correct word's tokens **72.9% of the time** with a mean expansion set of **367 tokens**. Worse on both axes than a real term dictionary.

### Where the trigram floor actually breaks

I claimed earlier in this investigation that shared trigrams never hit zero. That was an artifact of sampling words of length 5 and up. Stratified:

| word len |     n | mean shared | min | miss @cutoff>=2 | miss @cutoff>=1 |
| -------: | ----: | ----------: | --: | --------------: | --------------: |
|        2 |   281 |         0.1 |   0 |          100.0% |           86.5% |
|        3 | 1,022 |         0.7 |   0 |           89.3% |           41.5% |
|        4 | 2,931 |         1.5 |   0 |           49.5% |            5.6% |
|        5 | 2,963 |         2.4 |   1 |            9.8% |            0.0% |
|        6 | 2,945 |         3.4 |   2 |            0.0% |            0.0% |
|       10 | 2,958 |         7.3 |   5 |            0.0% |            0.0% |

Observations:

- **At length 3, 41.5% of edit-1 typos share zero trigrams.** `cat` and `at` share only `at$` out of 4 distinct padded trigrams, so a "share at least 2" cutoff misses a real neighbour.
- **From length 6 up the floor holds absolutely**, minimum 2 shared and a 0.0% miss rate at either cutoff. The q-gram count filter is sound on long words and unsound on short ones, which is exactly where a threshold cannot save you.

### The version that does work

Do the fuzzy match in character space, then map to token IDs, and never on the token ID sequence. Combining the vocab index with the bigram index gives a sound "does this document contain trigram `g`" primitive, which is a character-trigram index you never built:

```
  "doc contains trigram g"
      = OR over tokens whose string contains g       (vocab index, 2 MB)
     OR = OR over real adjacent pairs spelling g     (bigram index)
```

Cost is ~57 token lists per trigram at p50 instead of 1, but their union is exactly the set of documents containing that trigram, so posting volume is comparable. Against building a real document-trigram index at roughly 20 G postings and 50 GB, that is the cheapest route by a wide margin.

Two structural advantages carry over from Token Search. The term dictionary is **bounded at 200k and fixed**, so an automaton intersection can be precomputed offline and its cost is O(1) in corpus size, against a word dictionary that [keeps growing with every document](/blog/token-search#the-fix-normalize-before-you-tokenize) (146k terms for 52k docs). And token IDs are a **path-compressed trie**: a 12-character word is 2 or 3 token edges instead of 12 character nodes, and trie traversal is pointer chasing at ~75 ns per node while running the DFA across characters inside an edge is sequential at ~1 ns.

```
  char trie    t-o-k-e-n-i-z-a-t-i-o-n     12 random reads   ~900 ns
  token trie   [token]--[ization]           2 random reads   ~150 ns
```

The catch is that this gives **document-level** trigram containment, not word-level. Classic fuzzy matching scores similarity per term, and doc-level cannot tell "this document contains `tokenizaton`" from "this document is about tokenization and happens to contain those trigrams scattered around." So layer it: the virtual trigram filter shortlists documents cheaply, and a Levenshtein automaton over the word-tuple trie does the word-level match.

## Where this sits next to the Qdrant lexical design

I read [the Qdrant lexical search design doc](https://github.com/qdrant/qdrant) (`docs/superpowers/specs/2026-08-29-qdrant-lexical-search-design.md`, draft 2026-08-29) against this, and the honest answer is that they barely overlap.

|          | the design doc                     | this post                                |
| -------- | ---------------------------------- | ---------------------------------------- |
| question | which **terms** match this pattern | which **documents** contain this pattern |
| input    | pattern to term dictionary         | pattern to boolean over grams            |
| output   | TokenIds, then OR postings         | candidate docs, then verify regex        |
| scale    | dictionary, ~1M terms              | corpus, 10M docs                         |
| analogue | Elasticsearch `regexp` / `fuzzy`   | code search, grep                        |

The doc scopes mine out explicitly in Appendix A: "Not covered by this foundation: regex over full document text (code search). That needs document n-grams, a boolean planner, and a verification pass."

Where we do collide, the doc is right and I was wrong. Its Foundation 1 weighs an FST against vocabulary trigrams and picks the FST, rejecting trigrams on fuzzy recall with the `cat` versus `at` counterexample. My stratified table above is that rejection, measured: 41.5% zero-overlap at length 3. A Levenshtein automaton has no threshold and no misses by construction.

Three more flaws in my approach that the doc exposes:

- **Term identity.** The doc's sharpest design point is that vocab-trigram postings hold TokenIds rather than doc ids, which "preserves term identity, and therefore preserves real document frequencies and the synonym grouping machinery." My vocab index does hold token ids, but my straddle path resolves through the corpus bigram index and returns **documents**. With 77.6% of words needing that path, my structure almost always degrades to doc-level containment, so no df for the matched term, no equivalence grouping, no BM25 on the expansion. Fine for a filter, disqualifying for the doc's features.
- **Tokens-as-terms breaks the feature set.** If terms are BPE token IDs then `wildcard: "qdr*nt"` is meaningless and fuzzy recall is 72.9% against the FST's 100%. Foundation 1 requires terms to be words.
- **No scoring or pruning story.** The doc's Foundation 2 (TF postings, true field length, live `avgdl`, block-max with the C8 caveat that query-time normalisation loosens the bound) has no counterpart here. I was designing a filter and treating ranking as solved.

What this post contributes back, all of it inside Appendix A:

- **Appendix A has a factual error.** It says of the TopK approach that "adjacency is encoded inside the longer gram." Only with probability `2/((n-1)(n-2))`, so 1 time in 6 for a 5-character literal. That is why I measure an 8x false-positive rate on `/keniz/`.
- **If Qdrant builds that feature, build the bigram index and not sparse grams.** 19 GB against 75 GB, and measured, 3.25x fewer postings for identical candidate counts. The adjacency argument is real but did not pay, since the median mined literal is 6 characters and four ANDed trigrams are already near-exact.
- **The virtual trigram index makes a document-trigram index unnecessary**, 2 MB plus a bigram index against ~50 GB.
- **Caveat C4 has a conditional escape.** "FST is immutable, so there are two code paths" and "a latency cliff: the same query is fast on optimised segments and slow on a freshly written one." A fixed BPE vocabulary is known before any data arrives, so that FST is built once at collection creation, never merged, one code path, no cliff, and shared across fields rather than 45 MB each. This only works if terms are tokens, which breaks fuzzy, so it is an option for a token-native index alongside the word one, not a fix to the doc's design.
- **Caveat C10 has a measured middle answer.** The doc asks whether fuzzy variants share the original term's rarity and recommends sharing, scaled by edit distance. [Token Search's expansion weighting](/blog/token-search#closing-the-stemming-gap-token-natively) is a fitted version of exactly that: weight each variant by `df_variant / (df_variant + k * df_word)`, so a well-attested variant passes through and a rare coincidental one is damped, tested against Porter on 12 NanoBEIR sets.
- **One thing to check for C12.** Token Search found that splitting on `\w+` silently drops Unicode combining marks and shreds Devanagari and Thai into consonant skeletons, worth 0.28 NDCG. If Qdrant's `word` tokenizer uses a similar character class, that is a live multilingual bug rather than a design caveat.

The doc's framing beats mine on the point that matters most: synonyms, fuzzy, and stemming are one primitive, "group several terms into one statistical unit." Token Search reached the same place from the retrieval side and called it GroupCov plus stem-group expansion, and the doc generalises it correctly and wires it to three features instead of one.

## The plan

In the order I would build it.

1. **Word-aligned literal filtering on the existing unigram postings.** No new index, no new write path. Parse the regex into the AND/OR tree, keep only whole words, encode each with the leading-space normalisation, intersect. This is free and it covers the common case.
2. **Word-tuple keying as the filter key.** Already specified as Fix 1 in Token Search for IDF reasons. Reuse it here, store both keyings, subwords for BM25 partial matching and word tuples for filtering.
3. **The corpus token-bigram index.** 1.59x the unigram postings. Buys exact adjacency, which is the only measured latency win, and prunes the sub-word arm explosion by 670x to 236,907x. Prune the _dictionary_ hard by dropping any bigram above a document-frequency threshold, since a common bigram prunes nothing anyway, which cuts term-dictionary memory without touching the arms that matter.
4. **The vocab char-trigram sidecar.** 2 MB, static, built from the tokenizer at startup. Turns a sub-word literal into a candidate token set.
5. **Token-alphabet DFA verification.** Memoise `(state, token_id)`, drop the decode step.
6. **Only then, fuzzy.** And build it as a Levenshtein automaton over a word-tuple trie, not over token bags, for the reasons in the table above.

Items 1 and 2 need no new storage. Item 3 is the only real cost.

## What would falsify this

The candidate counts drive the entire latency table and I assumed them. The experiment that settles it is small: fix a corpus, fix roughly 200 regexes across the four classes (whole-word literal, sub-word literal, alternation, wildcard-heavy), and measure candidate-set size per method against dense trigrams, TopK sparse byte grams, token AND, word-tuple AND, and token sparse grams.

The headline is the **fallback rate**, the fraction of regexes where a method finds no usable constraint and has to scan. It is the direct analogue of Token Search's zero-rate, and it is where word-granularity filtering loses to TopK's character granularity. Everything else in the napkin table is arithmetic on constants.

Two more open threads I did not resolve:

- **Sparse grams over token IDs.** Run the CRC32 rule on token-ID pairs instead of character pairs. `E[grams] ~= 2L` with `L` in tokens is ~4x fewer entries for English, and each gram covers ~4x more text so it is rarer. I never measured it, and the invariant only holds if the token stream is locally determined, which it is at word granularity and is not for Chinese.
- **Content-defined tokenizer restarts for CJK.** Chinese uses naive tokenization with no presplit, so a span's tokens depend on the whole preceding run of non-space characters and the invariant dies. Cutting the text at CRC32 local maxima and tokenizing each chunk independently would restore it in every language, at some compression cost at the seams. This is the inverse of [Token Search's multilingual result](/blog/token-search#the-real-payoff-one-analyzer-every-language), where the config-free naive tokenizer was the thing that won.

## Reproducing

All four scripts run from the repo root and print incrementally.

```
python experiments/regex-filter/vocab_index.py       # sidecar sizing, fan-out, straddle rates
python experiments/regex-filter/arm_plan.py          # arm enumeration, bigram pruning, real alignments
python experiments/regex-filter/fuzzy_robustness.py  # BPE vs trigram under typos, by word length
python experiments/regex-filter/napkin.py            # storage and latency model
```

`arm_plan.py` builds its corpus from this repo's own `.mdx` and `.py` files chunked at 2,000 characters, so the absolute posting counts move with the repo. The ratios are what matter.

## Key Takeaways

- **Token postings filter regex in 0.96x the corpus size where TopK's sparse grams take 3.75x**, a 3.9x gap that comes entirely from a posting covering 4 bytes instead of half a byte. Latency ties on word-aligned patterns because fetch and verify dominate at 100 ms while traversal is 4 ms.
- **The adjacency argument did not survive measurement.** I predicted a token-bigram index would make `/keniz/` 5.2x faster, on the model that dense trigrams return 8x the true matches. They return 1.3x, so there was nothing for adjacency to remove. See [the benchmark](/blog/token-search-regex).
- **The bigram index prunes sub-word arm enumeration by 670x to 236,907x**, and the prune is sound rather than heuristic, since a pair that never occurs adjacently in the corpus cannot occur in any document of it.
- **The same structure fails on fuzzy search.** 39% of one-character typos share zero BPE tokens with the correct word, against 0% for char trigrams on words of 6 characters or more. BPE is a compression code and compression codes desync on one symbol.
- **Char trigrams have their own hole, at short words.** 41.5% of edit-1 typos on 3-letter words share zero trigrams, which is why the Qdrant design doc picks an FST over vocabulary trigrams and why that call is right.
- **Do pattern matching in character space and use tokens for storage and postings.** The two things Token Search contributes to fuzzy are a dictionary bounded at 200k and a trie path-compressed 4x, not the token representation itself.
