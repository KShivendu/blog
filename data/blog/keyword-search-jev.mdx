Some words matter more than others in a search query. Keyword search with BM25 doesn't really understand language, so it has to guess which ones. It gives rare words more weight, and it drops common words like `the`, `to` and `not` using a fixed stopword list.

Both guesses can be wrong. For the query "How do I improve on my math skills?", a rare word like `skills` matters very little, and a common word like `math` matters a lot. For "to be or not to be", the stopword list throws away every word, and nothing is left to search.

> Looking for TL;DR? Check [key takeaways](#key-takeaways)

I asked [Jev](https://openrouter.ai/docs/guides/community/jev), TypeSafe's decision model, how much each word matters in its query. One answer can fix both guesses. It raises the weight of the words that matter, and it tells which words are safe to drop. Then I trained a small model to copy the weights, so it's cheap enough to run on every query.

## Give the important words more weight

Take "films shot in Venice". In [a set of Wikipedia abstracts](https://huggingface.co/datasets/zeta-alpha-ai/NanoDBPedia), [BM25](https://en.wikipedia.org/wiki/Okapi_BM25) weights each word by its rarity, called inverse document frequency or IDF. `shot` is rarer, so it gets 5.39, while `Venice` gets 4.73.

But the location matters. A film shot in Malta doesn't answer this query. Can a model use the whole query to make a better guess about each word's importance?

I send Jev the whole query as context, with one question per word. Short queries fit in a single API request. For `Venice`, the prompt is:

```python
state = {"search_query": "films shot in Venice"}

question = {
    "type": "score",
    "instructions": (
        'The state is a user search query. How much does the word "venice" '
        "matter for finding documents relevant to this query?"
    ),
    "criteria": [
        "Irrelevant: dropping this word changes nothing",
        "Helpful but optional",
        "Essential: documents without it are wrong",
    ],
}
```

Jev returns a probability for each label. I use its probability of "Essential" as the importance score. It gives `Venice` 98% and `shot` 40%. Both weights increase, with a larger boost for `Venice`.

Compare the weights below. The relevant film, _Othello_, moves from fourth to third.

## Where Jev fits into BM25

BM25 scores each matching word using **strength of the match × word weight**, then adds those contributions. The match strength accounts for how often the word appears and the document's length.

I change the word weight by adjusting the document count used in IDF. For `Venice`:

1. It appears in **53 of 6,045 documents**, giving an ordinary IDF weight of **4.73**.
2. Jev gives it 98% importance. Treat its document count as `53 × (1 − 0.98) = 1.06`.
3. Recalculate IDF with that count: `ln((6,045 + 1) / (1.06 + 0.5)) ≈ 8.26`.

Here is the change in the formula. `df` counts documents containing the word, `N` is the total documents, and `p` is Jev's importance between 0 and 1:

<div className="jev-formula" tabIndex={0} aria-label="Word weight before and after adding Jev importance">

$$
\begin{aligned}
\text{BM25 weight} &= -\ln\!\left(\frac{\mathrm{df}+0.5}{N+1}\right) \\
\text{With Jev} &= -\ln\!\left(\frac{\mathrm{df}(1-p)+0.5}{N+1}\right)
\end{aligned}
$$

</div>

The replacement is **`df` → `df × (1 − importance)`**. BM25 uses the new weight in the same match-strength calculation.

Here `ln` is the natural logarithm. The `+0.5` and `+1` are the usual [IDF smoothing](https://lucene.apache.org/core/10_2_2/core/org/apache/lucene/search/similarities/BM25Similarity.html). They keep the weight finite even at 100% importance. At zero importance, we get ordinary IDF back.

The adjusted count changes the score. `Venice` still matches the same 53 documents. BM25's match strength and stemming stay the same. The default settings are `k₁ = 1.2` and `b = 0.75`.

## Let Jev pick the stopwords

Instead of a fixed list, I ask Jev which words are filler. I replace the first label in the prompt:

```python
question["criteria"][0] = (
    "Stopword: grammar or conversational filler; "
    "dropping it leaves the search intent unchanged"
)
```

The other two labels stay the same. The rule is simple. Turn off the static list, and drop a word only when Jev gives it **exactly 0%** Essential. Every word that stays gets the same weight formula as above. When words share a stem, the stem stays if any of them is above zero.

Take "to be or not to be" again. The static list drops every word. Jev keeps them all. It gives `to` 33%, `be` 68%, `or` 42% and `not` 61%.

The benchmarks have a real case too. Search for `"shall" vs. "will"`. The static list removes `will`, even though comparing those two words is the whole query. Jev gives `will` **87%**, so it stays. The relevant result, **“I will” or “I shall”**, moves to first place, and this query's nDCG@10 rises from **0 to 71.38**.

Dropping words is a separate choice from weighting them, so I test it on its own [below](#does-jev-beat-the-stopword-list). The weighting results and the distilled model use the static list.

## Distill Jev into a local model

Distillation means training a smaller model to reproduce a larger model's predictions. Here Jev supplies the word-importance labels. The small model reads the whole query in one pass and predicts those probabilities locally. Its predictions go into the same BM25 formula.

I trained both two-layer and six-layer MiniLM students. The two-layer [query-only model](https://huggingface.co/cross-encoder/ms-marco-MiniLM-L2-v2) uses 29,723 training queries. The six-layer version uses query-document pairs from 20,000 queries. The prediction and latency charts here show the two-layer model.

<details>
<summary>How do tokenizer pieces become word weights?</summary>

The model's tokenizer can split a word into several pieces. For "benefits of broccoli", it splits `broccoli` into `bro`, `##cco`, and `##li`. The `##` marks a continuation of the same word.

I train the prediction at the first piece to match Jev's importance for the whole word. The remaining pieces still provide context, but their predictions do not receive that training target. Here are the saved model's outputs for this query:

| Piece   | Importance prediction | Used for the word? |
| ------- | --------------------: | ------------------ |
| `bro`   |                 96.7% | Yes                |
| `##cco` |                 96.4% | No                 |
| `##li`  |                 69.6% | No                 |

The word gets 96.7% importance. Training explicitly assigns the whole-word target to the first piece. It does not force that piece to have the highest prediction. The pieces need not agree because I only use the first one's prediction.

The same stemming and stopword rules apply to every method. Words sharing a stem receive their highest Jev importance as a common training target. At search time, I also use the highest predicted importance among words sharing a stem.

</details>

## Does it improve search?

I compared the methods on the same **645 queries** across 13 [NanoBEIR](https://huggingface.co/collections/zeta-alpha-ai-nanobeir) datasets. They use the same stemming and the static stopword list. The default arms use the BM25 settings shown above.

I also tuned `k₁` and `b` separately for BM25, BM25 + Jev, and BM25 + the distilled model. For each dataset, I split the queries into five groups. I chose settings using four groups, then scored the fifth. Every query is scored using settings chosen on other queries.

The chart shows nDCG@10 (higher is better). You can switch between [p25, median and mean](/blog/stop-averaging-evals).

### Does Jev beat the stopword list?

Now the static list is off, and Jev's 0% rule decides which words to drop. Both columns use Jev's weights. On NanoBEIR, each column gets its own tuned `k₁` and `b`, the same way as above. The full collections use the default settings. Each cell shows **p25 / median / mean nDCG@10**.

| --------------------------- | --------------------: | ----------------------: |
| NanoBEIR, 645 queries       | 33.92 / 63.09 / 61.39 |   33.92 / 63.09 / 60.77 |
| Full FiQA, 648 queries      |     0 / 13.03 / 26.68 |       0 / 14.13 / 27.11 |
| Full English, 1,570 queries |     0 / 15.80 / 37.23 |       0 / 22.20 / 38.58 |
| Full Android, 699 queries   |     0 / 31.83 / 40.64 |       0 / 31.55 / 40.13 |

English gains **1.35 mean points**, with a 95% bootstrap interval of +0.77 to +1.93. FiQA gains 0.43. NanoBEIR loses 0.63 (interval −1.56 to +0.25) and Android loses 0.51. So Jev doesn't replace the list everywhere yet.

The rule drops a word only at exactly 0%, so small words that get 1% or 2% stay in. Sometimes that helps. In "can a ucc be filed on an individual", Jev keeps `a`, `be`, `on` and `an`, and quality rises from 20.44 to 60.53. Sometimes it hurts. Android's “How to Install App as System App” moves its relevant result from rank 1 to 9, and quality drops from 100 to 30.10.

## Key Takeaways

- BM25 uses rarity as a proxy for importance. Jev uses the query's context to adjust those weights. For "films shot in Venice", it gives `Venice` more weight than `shot` and improves the ranking.
- Use `df × (1 − importance)` as the effective document frequency, then apply the usual IDF smoothing. With both methods tuned, Jev raises mean quality from **59.79 to 61.39** on NanoBEIR.
- Letting Jev pick the stopwords keeps every word of "to be or not to be", which the static list drops. It helps full English (**+1.35**) and FiQA (+0.43) but costs NanoBEIR (−0.63) and Android (−0.51), so the static list stays for now.
- The two-layer distilled model reaches 60.26 and takes **3.19 ms median** per complete search, compared with about 508 ms for Jev. Its smaller quality gain has a bootstrap interval that includes zero.
